## Phase Goal

Sourced verbatim from `.planning/ROADMAP.md` Phase 1 `**Goal:**`:

> Owner can fully manage the bar's real inventory from their phone, with entries persisted to a live backend and reflected back immediately

**Planner note (surfaced, not silently fixed):** MVP mode expects this Goal line in "As a / I want to / so that" user-story form. It is not in that form, and per the MVP-mode rules the planner must not invent one. Run `/gsd mvp-phase 01` to convert the ROADMAP Goal line into a user story if that framing is wanted; planning proceeds on the substance of the goal, which is unambiguous.

<objective>
Stand up the Walking Skeleton for My Bar: a pnpm monorepo whose Fastify server owns a real SQLite file and serves the Barback SPA, proven end-to-end by the owner loading the Barback screen on their phone over the LAN and seeing real ingredient rows that survive a server restart.

This is the tracer slice for the entire project. Every later phase (recipes, the makeable engine, Patron, Bartender) builds on the architectural decisions committed here — see `SKELETON.md` in this directory, which is a contract, not a scratchpad.

Purpose: prove the whole stack works on one thin path before any feature breadth is added, so an architectural dead-end costs one commit instead of ten.
Output: working monorepo, live SQLite-backed read path, dark-themed antd Barback shell reachable from a phone, and a Vitest harness the rest of the phase writes tests into.
</objective>

<task type="checkpoint:decision" gate="blocking">
  <decision>What happens when the owner deletes a category that still has bottles in it?</decision>
  <context>
    This is the one part of the database schema that CONTEXT.md does not already settle, and it must be decided
    before Task 3 writes the tables — the answer becomes a foreign-key clause in the on-disk schema, so changing
    it after Phase 2's recipes start referencing categories means a data migration rather than a code edit.
    `01-RESEARCH.md` records it as assumption A3 at medium risk, and its Open Question 2 leaves the behaviour
    open. D-03 grants the owner delete capability but does not say what a delete should do to the bottles inside.
    Everything else about the data model is already locked by D-01 through D-07 and is not being re-asked here.
  </context>
  <options>
    <option id="refuse">
      <name>Refuse the delete and say why (planner recommendation)</name>
      <pros>Every bottle always keeps exactly one category, which is the invariant Phase 2's makeable matching
      assumes. The database enforces it, so no code path can orphan a row. The owner sees
      "This category is used by 4 ingredient(s) — reassign or remove them first." and stays in control.</pros>
      <cons>Clearing out a category the owner no longer wants takes two steps: move or delete the bottles first,
      then delete the category.</cons>
    </option>
    <option id="reassign">
      <name>Prompt to move the bottles to another category, then delete</name>
      <pros>One guided flow handles the whole job, and the invariant still holds.</pros>
      <cons>Needs a bulk-reassign screen no INV requirement asks for; `01-RESEARCH.md` Open Question 2 recommends
      deferring it. Would add a plan to this phase.</cons>
    </option>
    <option id="orphan">
      <name>Delete the category and leave its bottles without one</name>
      <pros>Delete always works immediately.</pros>
      <cons>Breaks D-02's one-category-per-ingredient rule. Those bottles would silently stop matching any recipe
      in Phase 2, which is exactly the "inventory quietly becomes untrustworthy" failure the project exists to
      avoid. The planner does not recommend this.</cons>
    </option>
  </options>
  <resume-signal>Select: refuse, reassign, or orphan. Selecting "reassign" or "orphan" requires replanning — plan 01-04 implements the "refuse" behaviour.</resume-signal>
</task>

## Planner Assumptions

No plain `01-SPEC.md` exists for this phase, so there is no `## Edge Coverage` section to lift. These edges were
identified by author judgment and are recorded rather than silently omitted:

- **Duplicate ingredient names are allowed.** The owner may genuinely own two bottles of the same product. Only
  `categories.name` carries a UNIQUE constraint, because D-01's typo-drift risk lives in the category taxonomy
  that Phase 2 matches against, not in bottle names. Confirm during UAT.
- **Whitespace-only names are rejected** by Zod's trim-then-min(1), so " " cannot create a nameless bottle.
- **`crypto.randomUUID()` is the id source** for both tables — available natively on Node 22 with no dependency.
- **Concurrent writes are last-write-wins.** Two devices toggling the same bottle resolve to whichever PATCH
  lands second; there is no row versioning. Correct at this scale, and revisitable in Phase 3 when Socket.IO
  makes concurrent edits visible.
