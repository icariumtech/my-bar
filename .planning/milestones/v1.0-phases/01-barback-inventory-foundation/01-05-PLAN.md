<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Owner-typed search text → React rendering | The only untrusted input this plan handles is the owner's own query string, which is echoed back in the no-matches message. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-20 | Tampering | Query string echoed into "No matches for '{query}'" | medium | mitigate | Render the query as a JSX text child so React escapes it. Never build that message through `dangerouslySetInnerHTML` or by assigning to `innerHTML`, which would turn the search box into a self-XSS vector on a shared kiosk device. |
| T-01-21 | Tampering | Ingredient and category names rendered in rows and chips | medium | mitigate | Same control: all server-supplied strings render as JSX text children and are escaped by React. Names originate from an unauthenticated write path, so they are treated as untrusted on output even though the owner is the expected author. |
| T-01-22 | Denial of Service | Client-side filter over the cached list | low | accept | The filter is a linear scan over roughly 50 to 100 in-memory objects per keystroke, which is imperceptible. Accepted with the constraint that no debounce is needed and no virtualization is added at this scale. |
| T-01-07 | Denial of Service | Absence of a server-side search endpoint | low | accept | Deliberate: filtering stays client-side, so no new unindexed `LIKE` scan is introduced into the synchronous better-sqlite3 driver (01-RESEARCH.md Pitfall 1). |
</threat_model>

## Planner Assumptions

No plain `01-SPEC.md` exists for this phase, so there is no `## Edge Coverage` section to lift. These search
edges were identified by author judgment and are recorded rather than silently omitted:

- **Search matches substrings, case-insensitively, across both bottle name and category name.** INV-04 says "by
  name or category" without specifying; one input covering both is the fewest decisions for the owner at the bar.
  Confirm at UAT.
- **No debounce.** The filter is synchronous and local, so debouncing would add latency to the one interaction
  that must feel instant.
- **Out-of-stock bottles are not hidden by any filter.** Filtering by stock state is not requested and is not
  built; the owner needs to see what is out in order to restock it.
- **An empty query with a category chip selected is a valid filter**, not treated as "no filter".
- **The filtered-empty and never-added states are distinguished by the unfiltered list's length**, not by the
  filtered result being empty — this is what stops a mistyped search from looking like data loss.
