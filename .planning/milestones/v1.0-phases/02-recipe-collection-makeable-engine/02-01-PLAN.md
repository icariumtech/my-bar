## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Barback client → POST/GET /api/recipes | Untrusted request body crosses into recipe/recipeIngredients writes and reads |
| recipes route → makeableEngine → ingredients table | Internal boundary: makeable computation must never be re-derived client-side |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-01 | Tampering | POST /api/recipes ingredient lines | high | mitigate | `categoryId`/`glasswareId` validated as `z.string().uuid()` at the Zod boundary; unknown-but-well-formed uuids trip the FK constraint and are translated to a fixed 400, never a raw 500 with SQLite's error text |
| T-02-02 | Denial of Service | POST /api/recipes body (name/method/garnish) | medium | mitigate | `.max()` bounds on every string field (name 200, method step 500, garnish 200, quantity 20) — same DoS mitigation pattern as Phase 1's ingredient/category inputs |
| T-02-03 | Information Disclosure | recipes.ts error handling | high | mitigate | FK/constraint errors caught and translated to fixed `{ error: string }` 400 bodies; raw SQLite message/stack never reaches the client |
| T-02-04 | Tampering | recipeIngredients.categoryId referential integrity | high | mitigate | DB-level `onDelete: 'restrict'` FK — a category still referenced by any recipe ingredient line cannot be deleted even if application-level checks are ever bypassed |
| T-02-05 | Repudiation | computeMakeable() correctness under client-side override | high | mitigate | makeable/missingCategoryIds/missingCategoryNames are computed exclusively server-side in this route; the shared `recipe` Zod schema is the only contract clients see, with no client-writable makeable field |
</threat_model>
