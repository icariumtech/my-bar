<objective>
Complete RECIPE-02 (edit/delete) on the backend, and extend Phase 1's category delete-guard (D-21) so a category still referenced by a recipe's ingredient lines is refused deletion exactly like one still referenced by an ingredient — with an accurate combined count. This plan closes the two backend gaps the tracer (02-01) deliberately left open: recipes could only be created, never changed or removed, and deleting a category ignored recipe references entirely.

Purpose: RECIPE-02 requires edit/delete; D-21 is a correctness requirement carried over and extended from Phase 1 — without it, deleting a category out from under a recipe would silently break that recipe's category-based matching (02-RESEARCH.md Pitfall 2).

Output: `PATCH`/`DELETE /api/recipes/:id`; `DELETE /api/categories/:id` now recipe-aware.
</objective>

    - PATCH with an ingredients array containing an unknown categoryId: 400, not 500.
    - DELETE /api/recipes/:id on an existing recipe: 204; a direct query of `recipeIngredients` for that `recipeId` afterward returns zero rows (cascade verified, not assumed).
    - DELETE on an unknown id: 404.
    - DELETE twice on the same id: first call 204, second call 404 (not a repeated 204).

    Add `PATCH '/:id'` to the existing `recipesRoutes` plugin in `apps/server/src/routes/recipes.ts`, schema `params: z.object({ id: z.string().uuid() })`, `body: recipePatch` (imported from `@my-bar/shared`, already defined in 02-01), response `{ 200: recipe, 400: errorObj, 404: errorObj }`. When `patch.ingredients` is present, wrap the replace in `db.transaction((tx) => { tx.delete(recipeIngredients).where(eq(recipeIngredients.recipeId, id)).run(); patch.ingredients!.forEach((ing, idx) => tx.insert(recipeIngredients).values({ id: crypto.randomUUID(), recipeId: id, categoryId: ing.categoryId, quantity: ing.quantity, unit: ing.unit, displayOrder: idx }).run()) })()` — better-sqlite3's synchronous transaction wrapper, called immediately, so a failed insert mid-loop rolls back the delete too (never a partially-replaced ingredient set). Apply the same conditional-field-set pattern `ingredients.ts` uses for its own PATCH (`...(patch.name !== undefined && { name: patch.name })`, etc.) for `name`, `method: patch.method !== undefined ? JSON.stringify(patch.method) : undefined`, `glasswareId`, `garnish`, plus `updatedAt: new Date()` unconditionally, applied via `db.update(recipes).set({...}).where(eq(recipes.id, id)).run()`. Wrap the whole handler body in `try/catch` translating `FOREIGN KEY constraint failed` to `400 { error: 'Unknown category or glassware' }`. After the writes, call the `loadRecipe(db, id)` helper from 02-01's Task 1; if it returns `undefined` (unknown id — the UPDATE matched zero rows), return 404.

    Add `DELETE '/:id'` with schema `params: z.object({ id: z.string().uuid() })`, response `{ 204: z.void(), 404: errorObj }`. Unlike categories/glassware, recipes have no downstream reference-count guard to build (nothing else references `recipes.id` except `recipeIngredients`, which is `onDelete: 'cascade'`) — check existence first (`db.select().from(recipes).where(eq(recipes.id, id)).all()`), 404 if absent, otherwise `db.delete(recipes).where(eq(recipes.id, id)).run()` and `reply.status(204).send()`. The cascade is the DB's job; no manual `recipeIngredients` delete is needed or should be added.
