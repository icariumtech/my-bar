## Accomplishments

- `CategoryPicker`: reusable `value`/`onChange`-shaped autocomplete field — case-insensitive substring search over existing categories, with a "+ Add" option that appears only when typed text matches no existing category (case-insensitively), creating the category inline via the existing `POST /api/categories` mutation and reporting its real id
- `AddEditIngredientView`: full-screen replacement for the Modal-based `AddEditIngredientForm` — identical Form, validation rules, and `useCreateIngredient`/`useUpdateIngredient` submit logic, with a `← Back` header replacing the Modal chrome and `CategoryPicker` replacing the old static `Select` + `renderCategoryPopup` inline-create pattern
- `IngredientsTab` now renders `AddEditIngredientView` full-screen (replacing the entire tab content, no double-render with the list) instead of opening the old Modal
- `AddEditIngredientForm.tsx` deleted — fully superseded, no remaining references

## Decisions Made

- `CategoryPicker` uses `AutoComplete`'s `onSearch` (fires while typing) plus `onSelect` (fires on committing a choice) rather than `onChange`, keeping "what the user is currently typing" (local `searchText` state) cleanly separate from "what has actually been selected" (the `categoryId` reported to the parent Form via `onChange`) — this directly matches the plan's instruction to render the selected category's *name* as display value while `onChange` always carries the *id*.
- `IngredientsTab` uses an early-return (`if (view === 'add') return <AddEditIngredientView ... />`) rather than the plan's literal `{view === 'add' && <.../>}` JSX fragment — behaviorally identical (the list is never rendered alongside the full-screen view), just expressed as a guard clause since the full-screen view now occupies the tab's entire render output rather than being layered inside it.

## Issues Encountered

**AutoComplete test-interaction pitfall (not a component bug):** While writing `AddEditIngredientView.test.tsx`'s submit test, typing the *exact* category name ("Rum") before clicking to select it made the test flaky/failing — antd's `AutoComplete` input wrapper renders its own `title` attribute mirroring whatever raw text is currently typed, so typing text identical to an existing option's label creates a `title` collision between that wrapper and the real dropdown option once categories finish loading (both would render `title="Rum"`), and Testing Library's `findByTitle` could resolve to the wrong (wrapper) element before the real category data had loaded. Root-caused via an isolated scratch test rendering `CategoryPicker` inside a bare `antd Form` and inspecting the DOM step by step (confirmed via console logging that clicking the wrapper never called the component's `onSelect` handler, while clicking a genuinely-rendered, unambiguous option did). Fixed by having the test type a partial substring ("Ru") instead of the full exact name — this is also more representative of real autocomplete usage and carries no ambiguity with the wrapper's mirrored title. No production code changed; `CategoryPicker.tsx` and `AddEditIngredientView.tsx` are unaffected by this finding.
