# Phase 02.1 Plan 05: IngredientPicker — Combined Category-or-Specific-Ingredient Autocomplete Summary

**A single antd AutoComplete field that searches both existing categories and existing specific ingredients, surfaces the "must be this specific ingredient" lock checkbox (D-28/D-30), and supports creating a brand-new ingredient inline (name + required category + in-stock switch) without leaving the recipe form (D-29).**

## Performance

- **Duration:** ~22 min
- **Completed:** 2026-08-11
- **Tasks:** 2
- **Files modified:** 4 (3 new, 1 modified — `.planning/REQUIREMENTS.md`)

## Accomplishments

- `IngredientPicker` — a standalone, reusable component exporting `IngredientPickerValue` (`{ categoryId, ingredientId, requiresSpecific }`) and `IngredientPickerProps` (`{ value, onChange }`) — the exact composite-value contract the later recipe-ingredient-line-wiring plan will consume
- Grouped AutoComplete options ("Categories" / "Ingredients" headings) with visually distinct labels (`"Rum"` vs. `"Havana Club (Rum)"`) so the owner cannot mistake a category selection for a specific-bottle selection (RESEARCH.md Pitfall 2)
- Selecting a category sets `{ ingredientId: null, requiresSpecific: false }` with no checkbox; selecting a specific ingredient sets `{ requiresSpecific: true }` (D-30 default-checked) and renders the lock checkbox
- Inline ingredient creation (D-29): `"+ Add new ingredient"` (case-insensitive duplicate-checked) reveals a self-contained sub-form — name (read-only, already typed), a required `CategoryPicker` (never pre-filled), and an in-stock switch — with Create disabled until a category is chosen
- The in-stock switch is functionally wired: since `POST /api/ingredients` has no `inStock` field (always defaults true per D-09), an unchecked switch triggers a follow-up `useToggleStock()` call after creation succeeds

## Decisions Made

- **Composite-value prop contract, not Form.Item cloning.** `IngredientPicker` accepts/emits `{ categoryId, ingredientId, requiresSpecific }` as plain props rather than relying on antd `Form.Item`'s automatic value/onChange cloning (which only carries one scalar). The plan explicitly assigns wiring responsibility (a `Form.Item noStyle shouldUpdate` render-prop) to the later recipe-form-assembly plan.
- **Stock switch wired to a real follow-up call, not left cosmetic.** See coverage D6 and the Deviations section below (Rule 2).
- **Display-text sync effect made lookup-miss-tolerant.** See Deviations below — prevents a blank-field flash immediately after inline ingredient creation.
- **CategoryPicker recreated as a blocking dependency.** See Deviations below (Rule 3).

- **Files modified:** `apps/barback/src/components/pickers/CategoryPicker.tsx` (new)
- **Verification:** `pnpm --filter barback test -- IngredientPicker` and `pnpm --filter barback build` both pass with this file present.
- **Committed in:** `7b89606` (Task 1 commit — created alongside the picker that needs it, ahead of task 2's actual use, since task 1's own build also imports nothing from it but task 2 does)

**2. [Rule 2 - Missing Critical] Wired the in-stock switch to an actual server effect**
- **Found during:** Task 2
- **Issue:** The plan's literal `useCreateIngredient` mutation payload (`{ name, categoryId, note: undefined }`) has no `inStock` field — `ingredientInput`'s Zod schema and the `POST /api/ingredients` route never accept one; new ingredients always start in stock (D-09, column default). As specified, the plan's stock-status switch would render but do nothing — toggling it off would silently have zero effect, contradicting D-29's "full add-ingredient flow: name + category + stock status."
- **Fix:** After a successful create, if the switch was left unchecked, issue a follow-up `useToggleStock({ id: created.id, inStock: false })` call before finalizing selection.
- **Files modified:** `apps/barback/src/components/pickers/IngredientPicker.tsx`
- **Verification:** New test `toggling the in-stock switch off before creating issues a stock-toggle call after creation` passes.
- **Committed in:** `af8223f` (Task 2 commit)

**3. [Rule 1 - Bug] Prevented a blank-field flash right after inline ingredient creation**
- **Found during:** Task 2, while reasoning through the display-text sync `useEffect`'s interaction with `useCreateIngredient`'s async `onSettled` invalidation
- **Issue:** The effect that keeps the AutoComplete's displayed text in sync with the controlled `value` prop looked up the selected id in the currently-fetched `ingredients`/`categories` lists and reset to an empty string on a lookup miss. Immediately after inline-creating a new ingredient, the `['ingredients']` query invalidated by `useCreateIngredient` hasn't refetched yet, so the newly selected id wouldn't be found in the stale list — the field would flash blank right after the owner just picked something, contradicting this plan's own must-have ("the newly created ingredient is immediately selected").
- **Fix:** The effect now only overwrites `search` when it finds an authoritative match; it never resets to empty on a miss. `handleCreateConfirm` already sets the correct display text synchronously at creation time, so this is purely defensive.
- **Files modified:** `apps/barback/src/components/pickers/IngredientPicker.tsx`
- **Verification:** Covered indirectly by the "completing the sub-form... onChange with the new ingredient selected" test (no flash observed); no dedicated flash-timing test was written since jsdom/React Testing Library doesn't reliably observe intermediate render frames.
- **Committed in:** `af8223f` (Task 2 commit)

## Issues Encountered

- **antd `AutoComplete` typing interaction under jsdom:** `fireEvent.change` on the underlying combobox `<input>` did not propagate to the component's controlled `search` state (rc-select's combobox mode input requires a real `input`-event sequence). Switched to `@testing-library/user-event`'s `userEvent.type()` for all typing interactions in the test file — resolved cleanly, no further issues.
- **Duplicate/ambiguous DOM matches when a nested picker (CategoryPicker inside the inline-create sub-form) opens its own dropdown:** antd's rc-motion "leave" transition keeps the outer `IngredientPicker` AutoComplete's previously-open dropdown mounted in jsdom (no animation-end event ever fires there), so `findByTitle('Rum')` could match both the stale outer dropdown's option and the freshly-opened `CategoryPicker`'s own option. Resolved by adding a `clickFreshestTitle()` test helper that selects the last-matching (most-recently-mounted, freshest-portal) element rather than assuming a unique match.
