## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] `form.getFieldValue`/`setFieldValue` inside the Form.List render-prop needed the full name path, not the plan's literal `[field.name, 'categoryId']` shorthand**
- **Found during:** Task 2 (Wire IngredientPicker into IngredientListForm), while writing `IngredientListForm.test.tsx`
- **Issue:** The plan's action text specifies reading/writing via `form.getFieldValue([field.name, 'categoryId'])` / `form.setFieldValue([field.name, 'categoryId'], ...)`. `[field.name, 'categoryId']` (e.g. `[0, 'categoryId']`) is only automatically resolved to the full path when a `<Form.Item name={...}>` is rendered *inside* `Form.List`'s own render-prop, because `Form.List` establishes a `FieldContext` with a `prefixName` that `Form.Item`'s internals consume. `Form.useFormInstance()`'s direct `getFieldValue`/`setFieldValue` methods are NOT scoped by that context — they operate against the form's flat internal store and require the complete path (`['ingredients', field.name, 'categoryId']`). Verified via a failing debug repro: selecting a category fired `IngredientPicker`'s `onChange` with the correct `categoryId`, but the subsequent `form.getFieldValue(['ingredients', 0])` read back `{ ingredientId: null, requiresSpecific: false }` with no `categoryId` key at all.
- **Fix:** Prefixed every `getFieldValue`/`setFieldValue` call in the render-prop with `'ingredients'` (`Form.List`'s own name), matching the form's actual flat store structure.
- **Files modified:** `apps/barback/src/components/IngredientListForm.tsx`
- **Verification:** `IngredientListForm.test.tsx`'s three tests pass, confirmed via a temporary debug test (removed before commit) showing the composite value round-tripping correctly.
- **Committed in:** `032a999` (Task 2 commit)

**2. [Rule 1 - Bug] `categoryId`/`ingredientId`/`requiresSpecific` were silently dropped from the actual recipe POST body — form.setFieldValue() alone does not register a Field entity**
- **Found during:** Task 3 (AddEditRecipeView), while writing the new specific-ingredient-lock submission test in `AddEditRecipeView.test.tsx`
- **Issue:** antd/`@rc-component/form` only includes a `Form.List` row's field in the values object passed to `onFinish`/`validateFields()` if that exact name path is registered via a `Form.Item` somewhere in the tree. `form.setFieldValue()` writes into the internal store but does not register a field *entity* — `validateFields()`'s value-collection step (`getFieldsValue(finalValueNamePathList)`) only clones paths belonging to registered entities, so an unregistered path is silently absent from the object even though `form.getFieldValue()` can still read it directly from the store. Since `IngredientPicker` writes `categoryId`/`ingredientId`/`requiresSpecific` purely via `form.setFieldValue` (the composite-value contract established in plan 02.1-05 — no `Form.Item name` binding of its own), all three fields were absent from the actual submitted recipe payload, despite `form.getFieldValue()` reflecting them correctly — this would have silently defeated the entire plan's stated purpose ("the recipe form is the only place `requiresSpecific`/`ingredientId` are actually set"). Verified via a failing test assertion before the fix (`capturedBody.ingredients[0].ingredientId` was `undefined`).
- **Fix:** Added three invisible `Form.Item` registrations per row (`name={[field.name, 'categoryId']}` etc., `noStyle`, wrapping a `NoRenderField` component that renders `null`) so each path is a real registered field entity. `IngredientPicker`'s own `onChange`-driven `form.setFieldValue()` calls continue to be the sole source of truth for these values; the invisible `Form.Item`s exist only to make antd include them in the values object it hands to `onFinish`.
- **Files modified:** `apps/barback/src/components/IngredientListForm.tsx`
- **Verification:** `AddEditRecipeView.test.tsx`'s new specific-ingredient test and both G-02-6 regression tests pass; `pnpm --filter barback test` (full suite, 51/51) and `pnpm --filter barback build` (zero type errors) both green.
- **Committed in:** `7fab83b` (Task 3 commit)
