# Phase 2.1: Recipe UI cleanup - Context

**Gathered:** 2026-08-11
**Status:** Ready for planning

<domain>
## Phase Boundary

Rebuild Barback's navigation from header-buttons-opening-stacked-modals to a persistent bottom tab bar (Ingredients / Recipes / Settings) with full-screen add/edit/detail flows. Replace static category/glassware dropdowns with a single autocomplete-with-inline-create field, applied consistently to ingredient categories, recipe-ingredient category-or-specific-ingredient selection, and recipe glassware selection. Extend the makeable engine so a recipe ingredient line can lock to one specific ingredient (not just its category) for non-substitutable items (e.g. lemon juice), with a tri-state per-line status (green/yellow/red) that rolls up to a recipe-level badge. This phase does NOT touch Patron/Bartender screens, AI features, barcode scanning, or unit-conversion — those remain out of scope per Phase 2's original boundary.

</domain>

<decisions>
## Implementation Decisions

### Navigation Architecture
- **D-23:** Replace the header's "Categories" / "Glassware" / "Recipes" buttons (which each open a Modal) with a persistent bottom tab bar with exactly 3 tabs: **Ingredients**, **Recipes**, **Settings**. The "My Bar — Barback" header title text is removed entirely. — **Reversibility:** costly — every screen's navigation entry point changes; reverting means rebuilding the header-button/modal shell.
- **D-24:** Settings tab houses both Categories and Glassware management (previously separate header buttons) — a menu/list linking to each, both as their own full-screen sub-pages (not sub-tabs). Exact Settings-tab internal layout (flat list vs. sectioned) is Claude's discretion.
- **D-25:** Ingredients and Recipes tabs each have an "Add {Item}" button in the upper-right corner of their screen (top app bar), replacing the current header-level "Add Ingredient" / "Add Recipe" buttons.
- **D-26:** ALL add/edit/detail flows become full-screen views with a back action, not modals — this applies uniformly to Ingredient add/edit, Category add/edit, Glassware add/edit, AND Recipe add/edit/view. No modal-on-modal stacking survives anywhere in Barback except small destructive confirmations (delete prompts stay as they are — out of scope for this change). — **Reversibility:** costly — touches every existing modal component's shell (App.tsx wiring + each form component's `open`/`onClose` props become route/view-state driven instead).

### Unified Autocomplete-with-Create Picker
- **D-27:** Replace static `<Select>` dropdowns with a single autocomplete-with-inline-"add new" text field pattern in three places: (1) an ingredient's category field (Ingredients tab add/edit), (2) a recipe ingredient line's category-or-specific-ingredient field, (3) a recipe's glassware field. Typing filters/searches existing entries; an "add new" affordance creates a new one inline without leaving the current form.
- **D-28:** The recipe-ingredient picker (item 2 above) searches BOTH categories and specific ingredients in one field — selecting a category behaves exactly like today (any in-stock member satisfies the line); selecting a specific ingredient additionally surfaces the "must be this specific ingredient" checkbox (see D-29/D-30).
- **D-29:** When the recipe-ingredient picker resolves to a specific ingredient that doesn't exist yet, the owner can create a brand-new ingredient inline from within the recipe form (full add-ingredient flow: name + category + stock status) — the recipe form is not restricted to picking only pre-existing ingredients.

### Specific-Ingredient Locking & Tri-State Makeable Status
- **D-30:** Each recipe ingredient line that resolves to a specific ingredient (not a plain category) gets a "must be this specific ingredient" checkbox. **Default: checked** (locked to that specific ingredient) — reasoning: booze lines are naturally selected at the category level already (so the checkbox is moot for them), while lines where the owner deliberately picks a specific ingredient (mixers like lemon juice) are usually non-substitutable, so defaulting to locked matches the common case. Unchecking it makes that line behave like a plain category match (the specific ingredient is kept as a display label/preference only). A line that resolves to a plain category (no specific ingredient chosen) has no checkbox — it always behaves like today's category-only matching.
- **D-31:** Makeable status becomes tri-state **per ingredient line**:
  - **Green** — the line's requirement is fully satisfied (a plain-category line has any in-stock member; a locked-specific line has that exact ingredient in stock)
  - **Yellow** — a locked-specific line whose exact ingredient is out of stock, but at least one other in-stock ingredient exists in the same category (a substitution is technically available even though the recipe says not to use it)
  - **Red** — nothing satisfies the line at all (plain-category line with zero in-stock members, or locked-specific line with its ingredient out AND no other category member in stock)
  — **Reversibility:** one-way — changes `computeMakeable()`'s return contract from boolean to tri-state per line plus a schema addition (`recipeIngredients.ingredientId` nullable FK + `requiresSpecific` boolean); every consumer of the old boolean `makeable` field (MakeableStatusBadge, RecipeList row rendering, RecipeDetailView) must be updated together.
- **D-32:** The **recipe-level** badge (shown in RecipeList rows and RecipeDetailView) rolls up per-line states as **worst-of-all-lines**: red if any line is red, else yellow if any line is yellow, else green. This is a genuine 3-state UI (not collapsed to 2), since the whole point is surfacing "makeable but with a substitution caveat" distinctly from "fully as intended."

### Claude's Discretion
- Settings tab's internal layout (flat list of two links vs. some other structure) — D-24 only locks that it's a single tab housing both.
- Exact visual treatment of the autocomplete component (antd `AutoComplete` vs. `Select` with `showSearch` + a synthetic "+ Add new" option row) — implementation detail for research/planning.
- Exact tri-state badge visual design (color + icon/text) — follows Phase 1/2's established accent(green)/destructive(red) tokens plus a new "warning" tone for yellow; specific token value is a UI-phase decision.
- Whether "Add {Item}" top-right buttons keep the existing 48px min-height touch-target convention — yes by default (Phase 1 D-13 precedent), not re-litigated here.

</decisions>

## Existing Code Insights

### Reusable Assets
- `apps/barback/src/components/CategoryManager.tsx`, `GlasswareManager.tsx` — current modal-based managers; their add/rename/delete logic (mutations, delete-guard handling) is reusable, only the shell (Modal → full-screen view) changes
- `apps/barback/src/components/RecipeForm.tsx`, `RecipeDetailView.tsx`, `RecipeList.tsx`, `IngredientListForm.tsx`, `UnitDropdown.tsx`, `GlasswareSelector.tsx` — existing recipe UI being restructured; form field logic (validation, submit handling) is reusable, layout/shell and the category/glassware Select components are being replaced
- `apps/barback/src/api/useRecipes.ts`, `useGlassware.ts`, `useCategories.ts`, `useIngredients.ts` — existing TanStack Query hooks and cross-entity invalidation pattern (established in Phase 2's gap-closure work: `useUpdateGlassware`/`useToggleStock` invalidate `['recipes']`) — new mutations (ingredient inline-create from recipe form, specific-ingredient lock toggle) should follow this same pattern

### Established Patterns
- antd dark theme (`ConfigProvider` + `darkAlgorithm` + token overrides) — unchanged, just applied to new full-screen views instead of Modals
- Fastify routes + Zod validation + Drizzle + SQLite `onDelete: 'restrict'` — the pattern MATCH-05's new `ingredientId` FK on `recipeIngredients` should follow (likely `onDelete: 'set null'` so deleting a specific ingredient degrades the line to category-only rather than orphaning/blocking, but this needs research/planning confirmation — not explicitly decided by the user)
- antd `Tabs` or a custom bottom-nav bar component — no existing precedent in this codebase; research should confirm the idiomatic antd v5/v6 pattern for a persistent bottom tab bar on a mobile-first layout (antd doesn't ship a native "bottom tab bar" component — likely a custom flex layout using antd `Segmented`/`Tabs` styled to the bottom, or a plain custom component)

### Integration Points
- `computeMakeable()` in `makeableEngine.ts` is the single integration point for D-31's tri-state logic — every consumer (recipes GET/POST/PATCH routes) flows through it
- `MakeableStatusBadge.tsx` is the single rendering integration point for the tri-state badge (D-32) — currently takes a boolean `makeable` prop, needs to take the tri-state value instead

</code_context>

<specifics>
## Specific Ideas

- Lemon juice vs. lime juice example: same category ("juice") but NOT interchangeable in a recipe — this is the concrete case driving D-30's specific-ingredient-lock default
- Booze categories (e.g. "Rye") are naturally substitutable — the owner expects category-level selection to remain the norm for spirits, which is why D-30 defaults new specific-ingredient selections to locked without making category-only selections need any checkbox at all
