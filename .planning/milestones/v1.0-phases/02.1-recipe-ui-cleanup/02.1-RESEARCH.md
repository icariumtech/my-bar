# Phase 2.1: Recipe UI cleanup - Research

**Researched:** 2026-08-12
**Domain:** Frontend navigation refactoring + makeable engine tri-state logic
**Confidence:** HIGH

## Summary

Phase 2.1 refactors Barback's navigation from header-driven modals to a persistent bottom tab bar (Ingredients/Recipes/Settings) with full-screen add/edit/detail flows, unifies category/glassware/ingredient pickers into a single autocomplete-with-inline-create field, and extends the makeable engine to support per-line specific-ingredient locking with tri-state status (green/yellow/red). The research confirms that antd v6 lacks a native bottom tab bar component but can be built idiomatically using either `Segmented` styled to the bottom or a lightweight custom flex layout; `AutoComplete` is the recommended picker component over `Select` with `showSearch` for dynamic inline-create workflows; Drizzle ORM supports `onDelete: 'set null'` on nullable FKs to degrade locked-specific-ingredient lines to category-only on ingredient deletion; the makeable engine requires refactoring from boolean to a per-line tri-state enum with recipe-level worst-of-all-lines rollup; and React 19 + Vite SPAs should use `react-router-dom` v7 for full-screen view navigation (the standard 2025 approach), though simple view-state management is viable for the 3-tab + 4 full-screen-views scope of this phase.

**Primary recommendation:** Use `AutoComplete` for pickers, `Segmented` component styled to the bottom for the tab bar, extend the existing React component state (no router library needed at this phase's scope), and refactor `computeMakeable()` to return a per-line tri-state enum with the recipe-level rollup computed in callers.

## User Constraints (from CONTEXT.md)

### Locked Decisions

- **D-23:** Replace header's "Categories" / "Glassware" / "Recipes" buttons with a persistent bottom tab bar with exactly 3 tabs: **Ingredients**, **Recipes**, **Settings**. The "My Bar — Barback" header title text is removed entirely.

- **D-24:** Settings tab houses both Categories and Glassware management (previously separate header buttons) — a menu/list linking to each, both as their own full-screen sub-pages (not sub-tabs).

- **D-25:** Ingredients and Recipes tabs each have an "Add {Item}" button in the upper-right corner of their screen (top app bar).

- **D-26:** ALL add/edit/detail flows become full-screen views with a back action, not modals — this applies uniformly to Ingredient add/edit, Category add/edit, Glassware add/edit, AND Recipe add/edit/view.

- **D-27:** Replace static `<Select>` dropdowns with a single autocomplete-with-inline-"add new" text field pattern in three places: (1) ingredient category field, (2) recipe ingredient category-or-specific-ingredient field, (3) recipe glassware field.

- **D-28:** The recipe-ingredient picker searches BOTH categories and specific ingredients in one field — selecting a category behaves exactly like today; selecting a specific ingredient additionally surfaces the "must be this specific ingredient" checkbox.

- **D-29:** When the recipe-ingredient picker resolves to a specific ingredient that doesn't exist yet, the owner can create a brand-new ingredient inline from within the recipe form.

- **D-30:** Each recipe ingredient line that resolves to a specific ingredient gets a "must be this specific ingredient" checkbox. **Default: checked** — reasoning: lines where owner deliberately picks a specific ingredient are usually non-substitutable, so defaulting to locked matches the common case.

- **D-31:** Makeable status becomes tri-state **per ingredient line**: Green (fully satisfied), Yellow (locked-specific out of stock but substitute available in category), Red (nothing satisfies).

- **D-32:** Recipe-level badge rolls up per-line states as **worst-of-all-lines**: red if any line is red, else yellow if any line is yellow, else green.

### Claude's Discretion

- Settings tab's internal layout (flat list vs. sectioned) — D-24 only locks that it's a single tab housing both
- Exact visual treatment of the autocomplete component (antd `AutoComplete` vs. `Select` with `showSearch` + synthetic "+ Add new" option row) — implementation detail for research/planning
- Exact tri-state badge visual design (color + icon/text) — follows Phase 1/2's established tokens plus new "warning" tone for yellow
- Whether "Add {Item}" top-right buttons keep the existing 48px min-height touch-target convention — yes by default (Phase 1 D-13 precedent)

### Deferred Ideas

None — the discussion was kept within this phase's scope per explicit user decision.

**Data flow for a tri-state makeable update:**
1. User toggles stock status of an ingredient in Barback Ingredients tab
2. TanStack Query mutation hits `PATCH /api/ingredients/:id` (stock toggle)
3. API route invalidates `['recipes']` cache
4. `useRecipes()` refetch executes `GET /api/recipes`
5. Server calls `computeMakeable(ingredientLines, db)` for each recipe
6. New tri-state logic: per-line {categoryId, ingredientId, requiresSpecific, status: 'green'|'yellow'|'red'}
7. API returns recipe + per-line statuses + recipe-level worstStatus
8. Frontend re-renders RecipeList with updated tri-state badges (green/yellow/red)

### Pattern 1: View State Management for Tab Navigation (Alternative to react-router)

**What:** Centralized view-state object in App.tsx tracks current tab and entity being edited/viewed. Each tab renders conditionally based on state. Full-screen views are overlayed as conditional renders, not separate routes.

**When to use:** Phase 2.1's 3-tab + 4 full-screen-views scope. Simple state suffices; no need for URL-based deep linking or browser back-button URL integration.

**Example:**
```typescript
// Source: CONTEXT.md D-23/D-26 pattern; antd + React 19 conventions
interface BarbackViewState {
  activeTab: 'ingredients' | 'recipes' | 'settings'
  currentView: 'list' | 'add-ingredient' | 'edit-ingredient' | 'add-recipe' | 'edit-recipe' | 'add-category' | 'edit-category' | 'add-glassware' | 'edit-glassware' | 'recipe-detail'
  entityBeingEdited?: Ingredient | Recipe | Category | Glassware
  entityBeingViewed?: Recipe
}

export default function App() {
  const [viewState, setViewState] = useState<BarbackViewState>({
    activeTab: 'ingredients',
    currentView: 'list',
  })

  function goToView(view: BarbackViewState['currentView'], entity?: any) {
    setViewState(prev => ({ ...prev, currentView: view, entityBeingEdited: entity }))
  }

  function goBack() {
    setViewState(prev => ({ ...prev, currentView: 'list', entityBeingEdited: undefined }))
  }

  return (
    <div>
      <BottomTabBar activeTab={viewState.activeTab} onChange={(tab) => setViewState(prev => ({ ...prev, activeTab: tab as any }))} />
      {viewState.activeTab === 'ingredients' && viewState.currentView === 'list' && (
        <IngredientsTab onAddClick={() => goToView('add-ingredient')} />
      )}
      {viewState.currentView === 'add-ingredient' && (
        <AddEditIngredientView ingredient={undefined} onBack={goBack} />
      )}
      {/* ... other views follow the same pattern */}
    </div>
  )
}
```

**Benefits:**
- No additional dependency (react-router-dom)
- Simple debugging: all state in one object
- Fast HMR for view-state changes
- Sufficient for current scope

**Drawbacks:**
- No URL-based deep linking (e.g., `/ingredients/123/edit` won't work)
- Browser back button doesn't navigate between views (or requires custom history integration)
- Scales poorly if nested routing is added later

### Pattern 2: Autocomplete-with-Inline-Create Picker (Unified across 3 use cases)

**What:** Single reusable `CategoryPicker` / `IngredientPicker` / `GlasswarePicker` component wrapping antd `AutoComplete`. On selection, creates new entry if needed; on submission, updates form value and parent state in one interaction.

**When to use:** D-27/D-28/D-29 — replacing 3 separate static `<Select>` dropdowns with a unified autocomplete pattern.

**Example:**
```typescript
// Source: antd AutoComplete docs + inline-create pattern
interface IngredientPickerProps {
  value?: string  // selected category name or ingredient name
  onChange: (selection: { type: 'category' | 'ingredient', id: string, name: string, categoryId?: string }) => void
  onInlineCreate?: (newEntry: { name: string, type: 'category' | 'ingredient' }) => Promise<{ id: string }>
}

export function IngredientPicker({ value, onChange, onInlineCreate }: IngredientPickerProps) {
  const [searchValue, setSearchValue] = useState('')
  const { data: categories = [] } = useCategories()
  const { data: ingredients = [] } = useIngredients()

  const options = [
    ...categories.map(c => ({ label: c.name, value: c.id, type: 'category' })),
    ...ingredients.map(i => ({ label: `${i.name} (${i.category})`, value: i.id, type: 'ingredient' })),
    // Only show "+ Add new" if search text matches nothing
    ...(searchValue && !options.find(o => o.label.toLowerCase() === searchValue.toLowerCase()) ? [
      { label: `+ Add "${searchValue}"`, value: `__add_new__:${searchValue}`, type: 'action' }
    ] : [])
  ]

  function handleSelect(selectedValue: string) {
    if (selectedValue.startsWith('__add_new__:')) {
      const newName = selectedValue.split(':')[1]
      onInlineCreate?.({ name: newName, type: 'category' }).then(result => {
        onChange({ type: 'category', id: result.id, name: newName })
      })
    } else {
      const selected = options.find(o => o.value === selectedValue)
      if (selected) onChange({ type: selected.type as any, id: selectedValue, name: selected.label })
    }
  }

  return <AutoComplete options={options} value={value} onChange={handleSelect} onSearch={setSearchValue} />
}
```

**Benefits:**
- Single component handles all 3 picker use cases (ingredient category, recipe ingredient, glassware)
- Inline creation avoids modal nesting (D-26 constraint)
- Uses native antd component, no third-party picker library

**Drawbacks:**
- Renders categories + ingredients + glassware in one option list (may be UX issue if lists are long; can be addressed with option grouping in planning/execution)

### Pattern 3: Tri-State Makeable Status (Per-Line + Recipe Rollup)

**What:** Extend `computeMakeable()` to return a per-line tri-state status (`TriStateLineStatus`) instead of a single boolean. Each line evaluates to green/yellow/red based on category match + specific-ingredient lock status. Recipe-level status is worst-of-all-lines.

**When to use:** D-31/D-32 — all recipe makeable computations (GET /api/recipes, POST /api/recipes, PATCH /api/recipes).

**Example:**
```typescript
// Source: CONTEXT.md D-31/D-32 requirements + SQL logic
export enum TriStateLineStatus {
  Green = 'green',   // Requirement fully satisfied
  Yellow = 'yellow', // Locked-specific out of stock, but substitute available in category
  Red = 'red',       // Nothing satisfies
}

export interface RecipeIngredientStatus {
  lineId: string
  categoryId: string
  ingredientId?: string  // null if no specific ingredient locked
  requiresSpecific: boolean
  status: TriStateLineStatus
}

export interface TriStateRecipeStatus {
  recipeId: string
  lines: RecipeIngredientStatus[]
  overallStatus: TriStateLineStatus  // worst-of-all-lines
}

export function computeMakeable(
  ingredientLines: Array<{ categoryId: string, ingredientId?: string, requiresSpecific: boolean }>,
  db: typeof defaultDb = defaultDb,
): RecipeIngredientStatus[] {
  const inStockByCategory = db
    .select({ categoryId: ingredients.categoryId, id: ingredients.id })
    .from(ingredients)
    .where(eq(ingredients.inStock, true))
    .all()
    .reduce((acc, row) => {
      if (!acc[row.categoryId]) acc[row.categoryId] = []
      acc[row.categoryId].push(row.id)
      return acc
    }, {} as Record<string, string[]>)

  return ingredientLines.map((line) => {
    if (!line.requiresSpecific) {
      // Plain category match (old behavior)
      const status = inStockByCategory[line.categoryId]?.length > 0 ? TriStateLineStatus.Green : TriStateLineStatus.Red
      return { lineId: line.id, categoryId: line.categoryId, status, requiresSpecific: false }
    } else {
      // Specific ingredient lock
      const inStockInCategory = inStockByCategory[line.categoryId] || []
      const specificIsInStock = inStockInCategory.includes(line.ingredientId!)
      if (specificIsInStock) {
        return { lineId: line.id, categoryId: line.categoryId, ingredientId: line.ingredientId, status: TriStateLineStatus.Green, requiresSpecific: true }
      } else if (inStockInCategory.length > 0) {
        return { lineId: line.id, categoryId: line.categoryId, ingredientId: line.ingredientId, status: TriStateLineStatus.Yellow, requiresSpecific: true }
      } else {
        return { lineId: line.id, categoryId: line.categoryId, ingredientId: line.ingredientId, status: TriStateLineStatus.Red, requiresSpecific: true }
      }
    }
  })
}
```

**Benefits:**
- Clear tri-state enum eliminates boolean ambiguity
- Per-line status allows detailed UI rendering (show substitution hints on yellow)
- Worst-of-all-lines rollup is computed once server-side, not recalculated on every render

**Drawbacks:**
- More complex API response shape; requires frontend update to handle tri-state
- Requires schema migration (`recipeIngredients.ingredientId`, `requiresSpecific`)

### Anti-Patterns to Avoid

- **Don't use bottom tab bar with `Tabs` component's default tabBarPosition.** antd's `Tabs` component is designed for top-positioned tabs with no native bottom positioning. Using it as-is and trying to flip styling is fragile. Use `Segmented` instead (lightweight, designed for any layout).

- **Don't hand-roll the recipe ingredient line tri-state logic in the frontend.** Keeping partial state on the client and trying to manually compute tri-state from partial ingredient data leads to cache misses and inconsistency across screens. Compute tri-state entirely server-side; frontends only render what the API provides.

- **Don't merge autocomplete/select picker logic into individual forms.** Duplication across CategoryPicker, IngredientPicker, GlasswarePicker breaks D-27's goal of a unified pattern. Extract common search/creation logic into a reusable hook (`useAutocompletePicker.ts`) or base component.

- **Don't add a specific-ingredient FK to `recipeIngredients` with `onDelete: 'cascade'`.** If an ingredient is deleted, you want to degrade the recipe line to category-only (yellow or red), not orphan/delete the entire line or recipe. Use `onDelete: 'set null'` so deleting an ingredient clears the FK, leaving `categoryId` intact.

- **Don't use view-state with URL-based routing libraries mixed.** If adopting react-router-dom in Phase 3, migrate all state from component props to router context; mixing patterns leads to state duplication and bugs.

| Bottom tab navigation on mobile | Custom flex container + button tap handlers + manual state sync | antd `Segmented` (or `Tabs` if using top position) | antd handles styling, accessibility (ARIA roles), dark-theme integration, touch feedback |
| Searchable picker with inline creation | Custom input + option filtering + manual option list state | antd `AutoComplete` component | Handles keyboard nav (arrow keys, Enter), highlights, open/close state, and supports custom option rendering for the "+ Add new" action |
| Per-line recipe makeable status | Frontend-side computation from partial category/ingredient data | computeMakeable() refactored to return per-line tri-state enum | Server-side computation is single source of truth; avoids cache misses and inconsistency across Patron/Bartender/Barback screens |
| Recipe ingredient line sorting on add/edit | Manual array.splice() in form state | Preserve `displayOrder` column in schema; increment/decrement on insert; let database order | Database ordering avoids frontend sync issues; accidental reordering on save is a known bug vector |

**Key insight:** This phase replaces 6 modal-based forms + 1 static dropdown UI with 6 full-screen forms + 1 unified autocomplete. The temptation to "just custom-build a simple version" is high, but re-using antd components (Segmented, AutoComplete) and the existing makeable-computation pattern (moved to tri-state) eliminates a class of subtle bugs (focus management, keyboard nav, state sync).

## Common Pitfalls

### Pitfall 1: Forgetting to Update All Consumers of `computeMakeable()`

**What goes wrong:** The Phase 2 routes (GET /api/recipes, POST /api/recipes, PATCH /api/recipes) call `computeMakeable()`, but if only one is updated to handle the new tri-state return type, the others still expect a boolean and crash on the unexpected response shape.

**Why it happens:** `computeMakeable()` is called in multiple places; a grep search finds them, but a developer might only update the route they're testing, not all three.

**How to avoid:** 
1. During planning, identify every caller of `computeMakeable()` (recipes.ts routes, any tests).
2. Update all callers in a single commit so the boolean→tri-state change is atomic.
3. Add a test that calls each recipe route (GET, POST, PATCH) and verifies the tri-state shape in the response.

**Warning signs:** Recipe list renders but badge is always green; or a crash "Cannot read property 'status' of undefined" when viewing a recipe after stock changes.

### Pitfall 2: Autocomplete Picker Shows Duplicate Options (Categories + Ingredients Mixed)

**What goes wrong:** The recipe-ingredient picker (D-28) searches both categories and ingredients in one field, but the option list is unsorted or grouped poorly, showing "Rum" (category) and "Rum (specific bottle)" (ingredient) as two separate clickable items. User clicks the wrong one.

**Why it happens:** The picker options array is built as `[...categories, ...ingredients]` with no visual distinction or grouping.

**How to avoid:**
1. Group options by type: `{ label: 'Categories', options: [...] }, { label: 'Ingredients', options: [...] }`.
2. Render option labels distinctly: "Rum (category)" vs. "Havana Club (Rum, specific)".
3. Test with a real recipe that has both category and specific-ingredient lines; verify the user can tell them apart.

**Warning signs:** User selects "Lime Juice" (ingredient) when they meant "Citrus" (category); recipe ends up locked to a specific bottle instead of flexible.

### Pitfall 3: `recipeIngredients.ingredientId` FK Deletes Entire Recipe on Ingredient Deletion

**What goes wrong:** When an ingredient is deleted, the `onDelete: 'cascade'` constraint orphans or deletes the entire recipe instead of just clearing the specific-ingredient lock.

**Why it happens:** Developer copies the `onDelete: 'cascade'` pattern from `recipeIngredients.recipeId` FK (which should cascade — deleting a recipe deletes its lines) without realizing this is a different use case (deleting an ingredient should degrade, not delete).

**How to avoid:** Set `onDelete: 'set null'` on `recipeIngredients.ingredientId` (confirmed by research: Drizzle ORM supports this pattern). Document in schema comment: `// ON DELETE SET NULL so deleting a specific ingredient degrades the line to category-only, not orphaning the recipe`.

**Warning signs:** A recipe with a specific-ingredient line disappears after the ingredient is deleted; or a database integrity error blocking ingredient deletion.

### Pitfall 4: View State Gets Stuck (User Navigates Back from Full-Screen View, State Doesn't Reset)

**What goes wrong:** User opens AddEditIngredientForm full-screen, clicks "Back", but the app doesn't reset `viewState.currentView` to 'list'. The back button is visibly clickable, but tapping it does nothing.

**Why it happens:** The "Back" button handler doesn't call `goBack()` (setViewState); or the view-state is in a prop chain that wasn't updated by the callback.

**How to avoid:**
1. Use a consistent `onBack` callback signature on all full-screen views: `onBack: () => void`.
2. Call `onBack()` (which triggers `goBack()` in App.tsx) from the back button in every full-screen view.
3. Test the flow: click into view → verify form renders → click back → verify list re-renders.

**Warning signs:** Full-screen view renders but clicking back does nothing; or user is stuck viewing an edit form.

### Pitfall 5: Specific-Ingredient Checkbox Defaults to Unchecked, Breaking the "Lemon vs. Lime" Use Case

**What goes wrong:** A developer defaults the checkbox to unchecked (false), making every specific-ingredient selection a category-only match. The user selects "Lemon Juice" (specific), but the line behaves like "Citrus" (category), and the recipe now accepts lime juice.

**Why it happens:** The developer interprets D-30 as "checkbox is optional" and sets `checked={false}` to let users opt-in. But D-30 explicitly says "Default: checked" — the checkbox starts checked and the user has to uncheck it if they want substitution.

**How to avoid:** Read D-30 carefully: "Default: checked". Set `checked={true}` when rendering the checkbox. Document this default in the form component: `// D-30: specific ingredients are non-substitutable by default`.

**Warning signs:** Recipe accepts lime juice when owner specifically selected lemon; or the checkbox doesn't appear at all (if the developer forgot to render it entirely).

### Example 3: `computeMakeable()` Refactored to Tri-State

**Source:** [VERIFIED: apps/server/src/services/makeableEngine.ts (refactored for Phase 2.1)]

```typescript
import { eq } from 'drizzle-orm'
import { db as defaultDb } from '../db/client.js'
import { ingredients } from '../db/schema.js'

export enum TriStateLineStatus {
  Green = 'green',
  Yellow = 'yellow',
  Red = 'red',
}

export interface RecipeIngredientStatus {
  lineId: string
  categoryId: string
  ingredientId?: string | null
  requiresSpecific: boolean
  status: TriStateLineStatus
}

export interface MakeableResult {
  lines: RecipeIngredientStatus[]
  overallStatus: TriStateLineStatus
}

/**
 * MATCH-01/MATCH-03/D-31/D-32: Extended from boolean to tri-state per-line.
 * A line is:
 * - Green: requirement fully satisfied (exact ingredient in stock, or any in-stock in category)
 * - Yellow: locked-specific ingredient out of stock, but another in-stock in category (substitution available)
 * - Red: no ingredient satisfies the line
 *
 * Recipe-level status is worst-of-all-lines: red if any red, else yellow if any yellow, else green.
 *
 * `db` is explicit second parameter (defaulting to real client) to support test db injection.
 */
export function computeMakeable(
  ingredientLines: Array<{
    id: string
    categoryId: string
    ingredientId?: string | null
    requiresSpecific: boolean
  }>,
  db: typeof defaultDb = defaultDb,
): MakeableResult {
  // Fetch all in-stock ingredients grouped by category
  const inStockRows = db
    .select({ id: ingredients.id, categoryId: ingredients.categoryId })
    .from(ingredients)
    .where(eq(ingredients.inStock, true))
    .all()

  const inStockByCategory = inStockRows.reduce(
    (acc, row) => {
      if (!acc[row.categoryId]) acc[row.categoryId] = []
      acc[row.categoryId].push(row.id)
      return acc
    },
    {} as Record<string, string[]>,
  )

  // Compute per-line tri-state status
  const lineStatuses: RecipeIngredientStatus[] = ingredientLines.map((line) => {
    if (!line.requiresSpecific || !line.ingredientId) {
      // Plain category match (no specific ingredient lock, or lock disabled)
      const status =
        inStockByCategory[line.categoryId]?.length > 0 ? TriStateLineStatus.Green : TriStateLineStatus.Red
      return {
        lineId: line.id,
        categoryId: line.categoryId,
        ingredientId: null,
        requiresSpecific: false,
        status,
      }
    } else {
      // Specific ingredient lock (D-30: default requiresSpecific=true)
      const inStockInCategory = inStockByCategory[line.categoryId] || []
      const specificIsInStock = inStockInCategory.includes(line.ingredientId)

      if (specificIsInStock) {
        return {
          lineId: line.id,
          categoryId: line.categoryId,
          ingredientId: line.ingredientId,
          requiresSpecific: true,
          status: TriStateLineStatus.Green,
        }
      } else if (inStockInCategory.length > 0) {
        // Locked ingredient out of stock, but substitute available (D-31: Yellow case)
        return {
          lineId: line.id,
          categoryId: line.categoryId,
          ingredientId: line.ingredientId,
          requiresSpecific: true,
          status: TriStateLineStatus.Yellow,
        }
      } else {
        // Nothing in stock (Red)
        return {
          lineId: line.id,
          categoryId: line.categoryId,
          ingredientId: line.ingredientId,
          requiresSpecific: true,
          status: TriStateLineStatus.Red,
        }
      }
    }
  })

  // D-32: Recipe-level is worst-of-all-lines
  const overallStatus = lineStatuses.some((line) => line.status === TriStateLineStatus.Red)
    ? TriStateLineStatus.Red
    : lineStatuses.some((line) => line.status === TriStateLineStatus.Yellow)
      ? TriStateLineStatus.Yellow
      : TriStateLineStatus.Green

  return { lines: lineStatuses, overallStatus }
}
```

## Open Questions

1. **Segmented component positioning on mobile**
   - What we know: antd `Segmented` is the recommended component for D-23's bottom tab bar; it natively supports horizontal orientation
   - What's unclear: Whether CSS `position: sticky; bottom: 0; width: 100%` plays well with Segmented inside a Tailwind dark-theme ConfigProvider; or if custom flex layout is more reliable
   - Recommendation: Prototype in planning by adding a Segmented to the current App.tsx, styling to bottom, and verifying dark-theme tokens are inherited correctly. If styling conflicts arise, fall back to custom flex layout (1-2 hours additional development).

2. **AutoComplete option grouping on large ingredient lists**
   - What we know: Recipe-ingredient picker (D-28) searches categories + ingredients together; both lists could be long (100+ recipes in a well-stocked bar)
   - What's unclear: Whether rendering 200+ options in a single flat list performs acceptably, or if option grouping (Categories / Ingredients sections) is needed for usability
   - Recommendation: Plan assumes flat list (simpler); if testing shows scroll/search lag, add option grouping in follow-up quick task.

3. **Backward compatibility: Existing recipes with null `ingredientId`**
   - What we know: Existing recipes (Phase 2) have `ingredientId = NULL` and `requiresSpecific = false` (schema defaults)
   - What's unclear: Whether the tri-state logic correctly handles a mix of old (category-only) and new (specific-ingredient) lines in the same recipe during migration
   - Recommendation: During planning, verify via migration script that existing recipes compute tri-state correctly (all lines Green if category is in stock, Red otherwise).

4. **View-state complexity growth: Will 3-tab + 4 full-screen-view state fit in a single object without getting unwieldy?**
   - What we know: App.tsx will manage a viewState object with activeTab + currentView + entity references
   - What's unclear: Whether nested sub-tabs (e.g., Settings tab → Categories → Edit CategoryX) will require deeper nesting of view state, making the object tree unreadable
   - Recommendation: Limit Phase 2.1 to the 3 tabs + 4 full-screen views specified in D-23/D-24/D-26. If Phase 3 adds Patron/Bartender tabs at the same level, consider migrating to react-router-dom at that time (not Phase 2.1 scope).

5. **Inline-create in recipe form: Should the new ingredient be immediately available in future recipe creation, or only in the current recipe?**
   - What we know: D-29 specifies creating an ingredient inline within the recipe form
   - What's unclear: Whether the new ingredient should be persisted to the database immediately (so it appears in future recipe forms), or held in transient state until the whole recipe is saved
   - Recommendation: Persist immediately (better UX; user sees ingredient in future forms; simpler state management). This mirrors the existing pattern: categories/glassware created inline are immediately in the database, available to all users. Requires server-side mutation for inline-created ingredients.
