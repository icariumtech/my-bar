<objective>
Close SYNC-01: wire a Socket.IO hub into the Fastify server that broadcasts `inventory:changed` after any ingredient write and `recipe:updated` after any recipe write, and wire the Patron client to invalidate its TanStack Query cache on those events (plus an explicit resync on every `connect`, including post-reconnect). This is the piece that turns 03-01/03-02/03-04's real-but-static read path into the phase's actual "live, trustworthy" guarantee.

Purpose: without this plan, Patron only ever shows the makeable status from the moment its page loaded — the project's stated Core Value ("the Patron and Bartender screens must correctly show which drinks are makeable right now... live") is unmet without it.
Output: `apps/server/src/ws/hub.ts` (new) wired into `buildApp()`; `inventory:changed`/`recipe:updated` emission in the ingredient/recipe routes, guarded so existing route-level tests are unaffected; `apps/patron/src/api/socket.ts` (new) wired into `main.tsx`.
</objective>

Export `registerSocketHandlers(socket: Pick<Socket, 'on'>, queryClient: QueryClient): void` — a pure wiring function taking a minimal structural type (just `.on`) so it's trivially testable with a fake object, no real `socket.io-client` instance needed in the unit test. ## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Any device on the LAN → Socket.IO connection | Unauthenticated, matching the project's existing no-auth REST API posture |
| Server → all connected Socket.IO clients | Broadcast-only; no server-side handler exists for any client-emitted event |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-12 | Tampering / Spoofing | Unauthenticated Socket.IO connections | medium | accept | Matches the project's existing T-01-04 no-auth decision (LAN-only, trusted friends/family, documented in `.claude/CLAUDE.md` and `REQUIREMENTS.md`'s Out of Scope); a connected socket can only RECEIVE broadcast events — this plan registers zero server-side `socket.on(...)` handlers for client-sent events, so there is no attacker-controlled input surface introduced by adding Socket.IO at all |
| T-03-13 | Denial of Service | Reconnect storms from multiple kiosk devices | low | accept | Socket.IO's built-in reconnection uses randomized exponential backoff by default; at this project's scale (three kiosk devices total per `PROJECT.md`), even a worst-case simultaneous-reconnect event is a handful of connections |
| T-03-14 | Information Disclosure | Emitted event payloads (`{ recipeId }`) | low | accept | A recipe id alone is not sensitive; no ingredient, stock, or inventory content is included in either event's payload — only a change signal. Actual data is fetched via the existing REST endpoints, which carry no additional exposure beyond what 03-01 already introduced |

</threat_model>
