<objective>
Give the owner full control of what is already in the system: edit any bottle's name, category, or size note, and curate the category taxonomy itself — add, rename, and delete — with a delete that refuses rather than orphaning ingredients.

Plans 01-01 through 01-03 made bottles creatable and toggleable. This plan closes INV-02 and delivers D-03's owner-managed taxonomy, which is also the integrity guarantee Phase 2's category-based makeable matching depends on.

Purpose: the inventory stays correct as the real bar changes — bottles get renamed, categories get reorganised.
Update endpoints for ingredients and categories, a delete guarded at the database, and the UI for both.
</objective>

    In `apps/server/src/routes/categories.ts` add `PATCH /:id` taking `categoryInput`, updating the name, and
    replying 200; a name colliding with another category raises the unique-constraint error, which must be
    caught and replied as 409. Add `DELETE /:id` which, before attempting the delete, counts the ingredients
    referencing that category. When the count is greater than zero, reply 409 with a JSON body carrying both an
    `error` string and an `ingredientCount` number so the client can render the exact count in its message.
    When the count is zero, delete and reply 204. Keep the database-level restrict rule as the real guard and
    treat the pre-count as the mechanism for a good error message, not as the enforcement: a check-then-act pair
    can be raced, so also wrap the delete and translate a constraint error into the same 409. Reply 404 for an
    unknown id.

    Extend both test files using `createTestDb()` and `.inject()`. Cover: patching an ingredient's name returns
    200 and persists, and leaves `inStock` untouched; patching only the note leaves name and category untouched;
    patching with an empty body returns 400; patching an unknown id returns 404; patching an ingredient onto an
    unknown category returns 400. For categories: renaming returns 200 and the ingredients in that category
    report the new `categoryName` through `GET /api/ingredients`, which is the regression guard proving
    ingredients reference the category by id rather than copying its name; renaming onto an existing name
    returns 409; deleting an unused category returns 204; deleting a category with two ingredients returns 409
    with `ingredientCount` equal to 2 and leaves both the category and its ingredients present in the database.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Phone browser → `PATCH /api/ingredients/:id`, `PATCH`/`DELETE /api/categories/:id` | Untrusted mutation and deletion of the taxonomy Phase 2's makeable matching depends on. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-16 | Tampering | `DELETE /api/categories/:id` | high | mitigate | Enforcement is the database's FK restrict rule with `foreign_keys = ON`, not the application's pre-count. The pre-count only builds the message; the delete is also wrapped so a constraint error raised by a racing insert becomes the same 409. Orphaning an ingredient from its category would silently corrupt Phase 2's matching. |
| T-01-17 | Tampering | `PATCH /api/ingredients/:id` body | high | mitigate | `schema.body` is `ingredientPatch`, derived from `ingredientInput` so all length bounds carry over; `stockPatch` remains a separate contract, so an edit request cannot alter stock state. |
| T-01-18 | Tampering | `:id` path parameters on both routes | medium | mitigate | `schema.params` constrains `id` to a uuid string on every new route, rejecting malformed ids before any query is built. |
| T-01-19 | Denial of Service | Empty or no-op PATCH bodies | low | mitigate | `ingredientPatch` refines to reject an empty object, so a no-op cannot consume a write path or report a false success. |
| T-01-11 | Information Disclosure | Constraint-error responses | low | mitigate | Unique- and foreign-key violations return fixed 400/404/409 shapes carrying only an `error` string and, for the delete case, a count. Raw SQLite error text never reaches the client. |
| T-01-04 | Spoofing | Unauthenticated taxonomy edits | medium | accept | Unchanged from plan 01-01: LAN-only trusted-household access is a documented project decision. |
</threat_model>

## Planner Assumptions

- **Resolves the UI-SPEC ⚠ unresolved CategoryManager empty state.** The zero-categories state shows a prompt to
  create the first category rather than a bare empty list. Plan 01-02 already removed the hard deadlock by
  allowing inline creation from the add-ingredient flow; this is the same affordance in the manager. Confirm the
  copy with the owner during UAT — the UI-SPEC deliberately left it undefined.
- **Category delete is refuse-only in Phase 1.** No guided "reassign these N ingredients to..." flow is built;
  `01-RESEARCH.md` Open Question 2 recommends deferring it, and no INV requirement asks for it. `ON DELETE`
  behaviour stays restrictive — the alternative of nulling or removing dependent rows would break the D-02
  invariant that every ingredient has exactly one category, which Phase 2's matching assumes.
- **Renaming a category is safe by construction** because ingredients hold `category_id`, never a copied name.
  The test asserting `categoryName` changes after a rename is the guard that keeps it that way.
- **Ingredient deletion is not in scope.** No INV requirement covers removing a bottle, and CONTEXT.md never
  raises it. Surface it to the owner at UAT if they expect it.
