<objective>
Extend the phase's core trust guarantee from boolean to tri-state: a recipe ingredient line can now lock to one specific ingredient, and the server computes green/yellow/red per line (MATCH-05), rolling up to a recipe-level overallStatus as the worst state across all lines (D-31/D-32). This is the phase's tracer — the schema, shared contracts, matching engine, and API route are wired for real here, with a real runnable test-backed proof, before any navigation/picker UI work begins. Because this changes computeMakeable()'s return contract from boolean to tri-state (a one-way door — see the checkpoint below), every existing consumer of the old boolean `makeable` field is updated atomically in this same plan, so the codebase never sits in a state where some components expect a boolean and others expect tri-state.

Purpose: MATCH-05 is the one genuinely one-way decision in this phase (CONTEXT.md D-31) — proving the tri-state computation is correct, including the adjacency edge case (a locked ingredient that's also its category's only member) and the atomic update of every existing consumer, de-risks the piece of business logic every later frontend plan in this phase builds on.

Output: `recipeIngredients` gains `ingredientId`/`requiresSpecific` columns, pushed to the dev DB; `packages/shared/src/makeable.ts` (new) + extended `recipe.ts` contracts; `computeMakeable()` returning per-line tri-state + recipe-level rollup with passing tests; `GET`/`POST`/`PATCH /api/recipes` returning real tri-state status; every existing Barback consumer of the old boolean `makeable` field updated to the new contract.
</objective>
