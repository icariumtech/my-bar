## Decisions Made

- Adjacency no-op (D-23/BARBACK-01) is satisfied entirely by antd `Segmented`'s underlying native `<input type="radio">` — clicking an already-checked radio never fires a DOM `change` event, so `BottomTabBar`'s `onChange` never fires and no state update happens. No guard code was written in `BottomTabBar.tsx` or `App.tsx`; this is a natural consequence of the component choice, not an implemented behavior.
- `SettingsTab` menu uses two full-width `Button`s (not a `List`) — both are explicitly allowed by the plan's action text ("a two-item List (or two full-width Buttons...)"), and `Button` matched the existing codebase's simpler affordance pattern more closely than introducing a new `List` usage for a 2-item menu.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Task 1's stated acceptance criterion for the adjacency no-op did not match antd `Segmented`'s actual behavior**
- **Found during:** Task 1 (BottomTabBar component) — while writing `BottomTabBar.test.tsx`
- **Issue:** The plan's acceptance criteria said "Clicking the already-active tab still fires `onChange` with the same value." Testing against the real antd `Segmented` component (which renders a native `<input type="radio">` per option) showed this is false: clicking an already-checked radio does not emit a browser `change` event, so `onChange` is never called for the already-active tab. This is actually the *correct* behavior for the adjacency no-op must-have ("Tapping the currently-active tab is a no-op") — it just isn't literally "firing onChange with the same value."
- **Fix:** Wrote the third `BottomTabBar.test.tsx` test to assert the real, natural behavior (`onChange` is NOT called when clicking the already-active tab) rather than forcing artificial logic to make a same-value `onChange` fire. This is simpler than the plan's originally described behavior and still satisfies the must-have truth and the plan's own framing ("the parent, not this component, is responsible for the adjacency no-op behavior") — the no-op is already guaranteed at the DOM level, so App.tsx needs no extra logic either.
- **Files modified:** `apps/barback/src/components/BottomTabBar.test.tsx`
- **Verification:** `pnpm --filter barback test -- BottomTabBar` passes (all 3 tests)
- **Committed in:** `1cfd46a` (Task 1 commit)
