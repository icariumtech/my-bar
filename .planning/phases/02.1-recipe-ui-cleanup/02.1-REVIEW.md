## Warnings

### WR-01: Ingredient creation + stock-toggle partial failure shows a misleading error and enables a duplicate on retry

**File:** `apps/barback/src/components/pickers/IngredientPicker.tsx:154-178`
**Issue:** `handleCreateConfirm` calls `createIngredient.mutateAsync(...)` and, if the owner unchecked "In stock", follows up with `toggleStock.mutateAsync(...)` inside the same `try` block:
```ts
const created = await createIngredient.mutateAsync({...})
if (!newIngredientInStock) {
  await toggleStock.mutateAsync({ id: created.id, inStock: false })
}
onChange({ categoryId: created.categoryId, ingredientId: created.id, requiresSpecific: true })
...
} catch {
  setCreateError("Couldn't create ingredient — check the name and try again.")
}
```
If `createIngredient` succeeds but the follow-up `toggleStock` call fails (network blip, etc.), the ingredient has already been persisted server-side, but the catch block reports "Couldn't create ingredient" — a misleading message — and leaves the `creating` sub-form open with the same typed name. `ingredients.name` has no uniqueness constraint (`apps/server/src/db/schema.ts:14-22`), so if the owner reads the generic error and clicks "Create" again, a second ingredient row with the identical name is created rather than the operation being treated as already-succeeded-but-incomplete.
**Fix:** Split the two calls' error handling, or check `created` before the `toggleStock` call fails, so the failure path calls `onChange`/`setCreating(null)` for the already-created ingredient and surfaces a narrower "Created, but couldn't set stock — edit it from the Ingredients tab" message instead of implying the whole creation failed:
```ts
const created = await createIngredient.mutateAsync({...})
onChange({ categoryId: created.categoryId, ingredientId: created.id, requiresSpecific: true })
setSearch(created.name)
setCreating(null)
setNewIngredientCategoryId(undefined)
setNewIngredientInStock(true)
if (!newIngredientInStock) {
  try {
    await toggleStock.mutateAsync({ id: created.id, inStock: false })
  } catch {
    setCreateError("Ingredient created, but couldn't set it out of stock — edit it from the Ingredients tab.")
  }
}
```

## Info

### IN-01: `PATCH /api/recipes/:id` cannot clear `glasswareId` back to "none"

**File:** `apps/server/src/routes/recipes.ts:278`, `packages/shared/src/recipe.ts:34`
**Issue:** `recipeIngredientInput`'s `glasswareId` is `z.string().uuid().optional()` (no `.nullable()`), and the PATCH handler only writes the field `patch.glasswareId !== undefined`. There is no way for a client to explicitly send `glasswareId: null` to clear a previously-set glassware back to "none" — the field is write-once-then-sticky via this route. This predates the 02.1 diff (unchanged by it) and isn't exercised by any `AddEditRecipeView`/`GlasswarePicker` flow in this file set, so it's informational rather than a regression, but worth a ticket since `GlasswarePicker` already supports clearing to `undefined` client-side (`GlasswarePicker.tsx:83-87`) with nowhere for that to actually land on an edit-then-save round trip.
**Fix:** Change `glasswareId` to `.nullable().optional()` in `recipeIngredientInput`/`recipeInput` (or a dedicated patch-only variant) and update the PATCH handler to write `null` through when explicitly sent.

### IN-02: Quantity/unit ingredient-line fields carry no client-side `rules`

**File:** `apps/barback/src/components/IngredientListForm.tsx:83-92`
**Issue:** The `categoryId`/`ingredientId`/`requiresSpecific` `Form.Item`s registered for `IngredientPicker` carry no `rules`, and the `quantity`/`unit` `Form.Item`s likewise have none — validation for a missing/invalid quantity or unit only happens server-side (`recipeIngredientInput` in `packages/shared/src/recipe.ts`), surfacing as a generic save-failure `Alert` rather than an inline per-field message. This is unchanged from the pre-02.1 file (not introduced by this diff) but is worth flagging since the surrounding form (name/category/method) does use inline `rules`-based validation elsewhere in the same view.
**Fix:** Add `rules` mirroring `recipeIngredientInput`'s constraints (`quantity`: required, max 20 chars; `unit`: required) to the corresponding `Form.Item`s for consistent inline feedback.
