    In `TagRail.tsx`, export two pure helper functions ahead of the component (Interface-First — logic before UI): `getActiveTagIds(recipes: Recipe[]): Set<string>` — iterates every recipe's `tags` array, collecting every `tag.id` into a `Set`. `filterRecipesByTag(recipes: Recipe[], tagId: string | undefined): Recipe[]` — returns `recipes` unchanged when `tagId` is `undefined`; otherwise returns `recipes.filter(r => r.tags.some(t => t.id === tagId))`. Both are exported so `RecipeBrowse.tsx` (Task 2) can import them directly rather than re-deriving the same logic.

    Define `const TAG_GROUP_META = [{ id: 'spirit', label: 'Spirit', Icon: Martini }, { id: 'type', label: 'Type', Icon: Sparkles }, { id: 'season', label: 'Season', Icon: Leaf }, { id: 'flavor', label: 'Flavor', Icon: Flame }] as const` (import `Martini, Sparkles, Leaf, Flame` from `lucide-react` — verified exact export names against `lucide-react@1.31.0`'s own `dist/lucide-react.d.ts`, not assumed) — iterate `TAG_GROUP_META` in this fixed order (mirrors `TAG_GROUP_ORDER` from `@my-bar/shared`, kept as a local literal here since the icon mapping is UI-only and doesn't belong in the shared package).

    `TagRail({ recipes, selectedTagId, onSelectTag }: { recipes: Recipe[]; selectedTagId: string | undefined; onSelectTag: (tagId: string | undefined) => void })`: computes `activeTagIds = useMemo(() => getActiveTagIds(recipes), [recipes])`. For each group in `TAG_GROUP_META`, additionally needs each group's actual `Tag` objects (id/name) to pass to `TagSubmenu` — derive them by collecting `recipes.flatMap(r => r.tags).filter(t => t.group === group.id)`, de-duplicated by id (a `Map` keyed by `tag.id` is the simplest de-dupe), then filtered to `activeTagIds.has(t.id)` (redundant with the flatMap source but keeps the filter explicit and future-proof if a non-recipe-sourced tag list is ever substituted) — this doubles as the "does this group have anything to show" check: a group with zero resulting tags renders its icon at reduced opacity (`opacity-40`, non-interactive — no `onClick`, no expand state) per D-36. A group WITH tags is a tappable button toggling a local `expandedGroupId` state (only one group's submenu open at a time; tapping the already-expanded group's icon again collapses it — ordinary accordion behavior, not part of D-37's tag-selection rule).

    `TagSubmenu({ tags, selectedTagId, onSelectTag }: { tags: Tag[]; selectedTagId: string | undefined; onSelectTag: (tagId: string) => void })`: renders each tag as a tappable pill/button, highlighted (`bg-patron-accent`) when `tag.id === selectedTagId`. Each button's `onClick` calls `onSelectTag(tag.id)` — the toggle-to-clear behavior (tapping an already-selected tag clears it) is implemented in the PARENT `TagRail`'s handler, not here: `TagRail` passes a wrapped callback to `TagSubmenu` — `(tagId) => onSelectTag(tagId === selectedTagId ? undefined : tagId)` — keeping `TagSubmenu` itself a dumb, reusable list renderer with no awareness of the clear-on-retap rule.

    Layout: `TagRail` is a fixed-width (`w-16` or similar, Claude's discretion per UI-SPEC) vertical flex column (`flex flex-col gap-md items-center`) on the left; each group's `TagSubmenu`, when expanded, renders directly beneath that group's icon (not as a separate overlay/popover) so the rail's own height grows — simplest correct layout for a kiosk-sized iPad viewport, matching the reference photo's rail-with-inline-expansion behavior.
