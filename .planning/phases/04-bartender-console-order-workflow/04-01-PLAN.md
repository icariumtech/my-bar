## Phase Goal

Sourced verbatim from `.planning/ROADMAP.md` Phase 4 `**Goal:**`:

> A patron can submit a real order that flows live into the bartender's queue, and the bartender can fulfill it using the same trusted recipe/inventory data, while the Patron screen behaves like an unattended kiosk

**Planner note (surfaced, not silently fixed):** MVP mode expects this Goal line in "As a / I want to / so that" user-story form. It is not in that form — it names two actors (patron, bartender) whose stories genuinely differ, so collapsing it into one single-actor sentence would flatten scope rather than clarify it. Per the MVP-mode rules the planner must not invent one — the same situation Phase 1's `01-01-PLAN.md` and Phase 3's `03-01-PLAN.md` both recorded, and both planned proceeding on the substance of the goal, which is unambiguous. Run `/gsd mvp-phase 04` if the user-story framing is wanted; this plan set proceeds on the goal's substance.

## Planner Assumptions (spec-less probe fallback, phase-wide)

No plain `04-SPEC.md` exists for this phase, so the deterministic edge-probe report supplied in the planning context and `04-UI-SPEC.md`'s own `## UI Considerations` table are the source for edge coverage instead of a SPEC's `## Edge Coverage`/`## Prohibitions` sections. Every probe item was resolved (never silently dropped) and threaded into `must_haves` on the plan that implements it:

- PATR-05 empty/encoding/idempotency/concurrency (all resolved explicit, this plan): see must_haves above.
- PATR-07 (unclassified → resolved explicit, Plan 04-05): fullscreen request failure degrades gracefully, app continues.
- PATR-08 (unclassified → resolved explicit, Plan 04-05): inactivity timeout resets on touch/mouse/key events, fires exactly once per idle period.
- BART-01 (unclassified → resolved explicit, Plan 04-02): a recipe with null glassware/garnish/description renders the existing "None specified"/omitted-section convention already proven in Barback's RecipeDetailView — not a new gap this phase introduces.
- BART-02 (unclassified → resolved explicit + one backstop, this plan): see must_haves above (live-queue proof + reconnect-catch-up assumption).
- BART-03 (unclassified → resolved explicit, Plan 04-03): repeat-PATCH on an already-'done'/already-'in_progress' order is a safe idempotent no-op, not an error — matches the project's existing idempotent-PATCH convention (e.g. the stock toggle).
- BART-04 adjacency/empty/ordering (all resolved explicit, this plan): see must_haves above.
- BART-05 empty/encoding (resolved explicit, Plan 04-02): empty query + no tags selected returns the full unfiltered list; name matching is case-insensitive substring on trimmed input, mirrors Barback's RecipeList.tsx convention exactly.
- BART-06 adjacency/empty/ordering (resolved explicit, Plan 04-02): Bartender renders `recipe.overallStatus`/ingredient `displayOrder` exactly as the server returns them — never re-derived or re-sorted client-side; a zero-ingredient recipe cannot exist (recipeInput.ingredients.min(1), enforced since Phase 2).
- SYNC-02 boundary/precision (resolved explicit, Plan 04-03 for the retention-window boundary; this plan for the elapsedSeconds floor): see must_haves in both plans.

`04-UI-SPEC.md`'s "## UI Considerations" is lifted identically: Patron Order Submission's empty/loading/error rows and the Bartender Orders Tab's empty/loading/error rows land in this plan (the components that render them exist here); the Patron "populated" backstop also lands here. Bartender Recipes Tab rows land in Plan 04-02. Bartender Orders Tab's batched/long-text rows and Patron Kiosk Inactivity's rows land in Plans 04-04/04-05 respectively.

Two prohibition-probe survivors (Stage 1 recall → Stage 2 precision; routine-engineering and OWASP-canon candidates dropped) are threaded into `must_haves.prohibitions` on the plans that build the surface they constrain: (1) the Bartender console must never expose recipe/ingredient/tag mutation actions — it is read-only lookup (Plan 04-02); (2) marking an order Done must never touch ingredient stock/inventory records (Plan 04-03).
