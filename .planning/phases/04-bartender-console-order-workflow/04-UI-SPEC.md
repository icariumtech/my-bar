# Phase 4 — UI Design Contract

> Visual and interaction contract for the Bartender console app + Patron order workflow. Generated by gsd-ui-researcher from upstream decisions (04-CONTEXT.md, 04-RESEARCH.md) and existing design system (Phases 1–3).

| Property | Value |

| Preset | not applicable |

## Surface Inventory

### apps/bartender (NEW)

**Target Hardware:** Amazon Echo Show 8 Gen 1 (LineageOS, ~8" portrait/landscape touchscreen)

**Theme:** antd `darkAlgorithm` utility dark theme (matching Barback, **not** Patron's neon)

**Layout:** Two-tab interface (BottomTabBar) — Recipes / Orders

**Key Views:**
- RecipesTab: searchable recipe list with tag/name filter (taps into shared RecipeDetail)
- OrdersTab: active orders queue with elapsed time, batched by recipe (taps into shared RecipeDetail + Done button)
- RecipeSearchFilter: full-screen tag picker + name search overlay
- RecipeOrOrderDetail: shared detail view (shows full recipe, tri-state makeable status, conditional Done button)

### apps/patron (MODIFIED)

**No visual theme changes.** Existing dark-neon aesthetic (Phase 3) remains unchanged.

**New Components:**
- Order button + disabled state (conditional display on RecipeDetail when recipe is makeable)
- OrderPrompt: modal overlay for "who's this for" text input

**New Hooks:**
- useKioskInactivity: idle detection + timeout callback
- useFullscreen: iPad Safari fullscreen API wrapper
- useWakeLock: screen wake-lock acquire on app load
- useSubmitOrder: POST /api/orders mutation

## Copywriting Patterns

### Tone
- **Bartender:** utilitarian, direct, action-oriented (mirrors Barback phase 2.1 tone)
- **Patron:** friendly, encouraging, never technical (existing phase 3 tone, unchanged)

### Destructive Actions
**None explicitly destructive this phase.** Order submission is reversible (user submits, can submit again immediately per D-53). No order deletion, ingredient deletion, or recipe deletion flows in Phase 4.

### Empty States
All empty states include context + next step:
- Orders queue empty → "Queue is empty. Waiting for guests to order..." (no action needed; system is working normally)
- Search results empty → "No recipes match your search" (suggests refining search)

### Error States
All errors include problem + recovery path:
- Network error → "Failed to load X. Check your connection." + Retry button
- Order submission error → "Failed to send order: {specific error}" + Retry prompt

## Interaction Patterns

### Bartender Order Workflow (D-55 through D-60)

**Status Lifecycle:** new → in_progress (auto on tap into detail) → done (manual Done button)

1. **Submit (Patron RecipeDetail):** Tap Order → OrderPrompt modal → enter optional name → Send Order → POST /api/orders → toast "Order sent to bartender!" → return to browse grid
2. **Receive (Bartender Orders tab):** Socket.IO orders:created event → invalidate ['orders'] → re-fetch → new order appears in list
3. **Fulfill (Bartender):** Tap order in list → auto-advance to in_progress → view RecipeOrOrderDetail → review ingredients + method → tap Done → PATCH /api/orders/:id/done → Socket.IO orders:updated → invalidate ['orders'] → order badge decrements → order moves to done pile
4. **Cleanup (Server):** Done orders remain visible briefly (D-60); auto-remove after 5 minutes server-side (soft-delete via deletedAt timestamp or move to archive table) OR filter client-side on fetch

**Batching (D-58):** Client-side grouping in OrdersTab — fetch flat list, batch by (recipeId, status), show one row per batch with ×N count and aggregated patronNames list.

**Elapsed Time (D-59):** Display as relative time ("2m ago", "45s ago") computed server-side in GET /api/orders response (Date.now() - createdAt), updated on each refetch (no live clock in UI).

### Patron Kiosk Behavior (D-50, PATR-07, PATR-08)

1. **App Load:** Request fullscreen (App.tsx useEffect) → Request wake-lock (App.tsx useEffect) → Display browse grid
2. **Inactivity Detection:** useKioskInactivity hook listens to touchstart, mousedown, keydown → resets 90-second timer on each event → on timeout: navigate back to RecipeBrowse (home grid)
3. **User Returns:** Browse → tap recipe → detail → can order again
4. **Fullscreen Exit (iPad):** If fullscreen exits unexpectedly (e.g., input focus on iPad — A4 pitfall), app continues to function (no crash); user can manually re-enter fullscreen via device controls

**Timeout Duration (PATR-08 discretionary):** 90 seconds (middle of 60–120 range, balance between not interrupting users mid-use and not leaving kiosk active too long after departure).

## UI Considerations

> State coverage for empty, loading, error, and populated states. Entries follow the probe-core format (✅ covered / 🧪 backstop / ⚠ unresolved).

### Patron Order Submission

| Category | Element | Status | Resolution |
|----------|---------|--------|------------|
| empty | Order button on detail screen when recipe is not makeable | ✅ covered | Button is disabled (opacity/pointer-events) or hidden (display: none) per D-49; copy "Not available" may appear on hover |
| loading | Order submission in progress | ✅ covered | Button text changes to "Sending..."; button disabled; spinner optional |
| error | Order submission fails (network or server error) | ✅ covered | Alert rendered on RecipeDetail with error message per "Order submission error" copy; Retry prompt visible; user can tap Order button again |
| populated | Order submitted successfully | 🧪 backstop | Toast "Order sent to bartender!" appears; auto-dismiss after ~3s; navigation back to browse grid (no persistent post-submit view per D-51) — manual test required on real device to confirm toast timing and navigation |

### Bartender Recipes Tab

| Category | Element | Status | Resolution |
|----------|---------|--------|------------|
| empty | Recipe list when no recipes exist | ⚠ unresolved | Assumption: System always has ≥1 recipe by Phase 4 (Phase 2 seeded recipes); planner may override if starting from blank DB |
| loading | Recipe list fetch in progress | ✅ covered | Spinner displayed in tab content area; "Loading..." text optional |
| error | Recipe fetch fails | ✅ covered | Error message "Failed to load recipes. Check your connection." + Retry button per copywriting contract |
| overflow | Recipe list >100 items on 8" screen | 🧪 backstop | Assumes virtualization (antd List supports this) or infinite scroll; manual test on Echo Show device required to verify no UI cutoff or performance lag |

### Bartender Orders Tab

| Category | Element | Status | Resolution |
|----------|---------|--------|------------|

## Appendix: Discretionary Decisions Summary

| Decision | Value | Rationale |
|----------|-------|-----------|
| Inactivity timeout (PATR-08) | 90 seconds | Middle of 60–120 recommended range; balances UX (not interrupting mid-use) with ops (prevents long idle on wall-mounted device) |
| Done order retention (D-60) | 5 minutes (soft-delete server-side or filter client-side) | "Briefly" = practical window for bartender to see recent history without unbounded queue growth |
| Orders badge count | Count "new + in_progress" only | Shows all open tickets needing attention; excludes done orders (already auto-hiding) |
| Batched order visual | Inline ×N badge + aggregated names list | Follows antd List item pattern; consistent with Barback's existing list conventions |
| Elapsed time display | "{N}m ago" relative format, server-computed | Human-readable; no live clock needed (re-fetched on each update via TanStack Query) |
| Patron fullscreen | Request on App.tsx mount | Single call point reduces failure modes; graceful degradation if denied |
| Wake-lock | Request on App.tsx mount | Screen stay-on for wall-mounted kiosk; graceful failure if denied (app continues) |

## Notes for Planning & Execution

1. **No Patron theme changes:** RecipeDetail Order button and OrderPrompt modal use existing Patron neon tokens (orange `#ff6b35`, cyan `#4dd0e1`). Do not apply Bartender's antd dark theme to Patron modifications.

4. **Test on real devices:** Kiosk fullscreen/wake-lock behavior and 8" screen rendering must be verified on actual iPad Safari + Echo Show LineageOS device. Simulator behavior may differ.
5. **Pitch DX concern:** No UI/UX regressions on Patron — all Phase 3 components, styles, and interactions remain unchanged.
