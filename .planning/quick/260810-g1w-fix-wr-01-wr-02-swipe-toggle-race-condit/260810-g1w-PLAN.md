<objective>
Fix two race conditions in `IngredientRow.tsx`'s swipe-to-toggle logic, flagged as WR-01
and WR-02 in the phase 01 code review (`01-REVIEW.md`), without changing the swipe/undo
interaction model (left = out-of-stock, right = in-stock, deferred commit behind a
3-second undo grace timer, no network request on undo — D-08, D-10).

of truth — a stock toggle that visually flickers back to the stale value mid-commit (WR-01),

unmounts before the grace period elapses (WR-02), both directly undermine that guarantee.

value survives the async commit round-trip and a still-undoable pending toggle is flushed
(not dropped) on unmount. `pnpm --filter barback build` and
`pnpm --filter barback exec tsc --noEmit` both pass clean.
</objective>

  <action>
Rework the component's local state and effects so the two review findings are fixed while
`displayedInStock = pending ?? ingredient.inStock` and the swipe/undo gesture wiring stay
exactly as they are today.

State: keep the existing `pending: boolean | null` state (the optimistic value to
display) exactly as-is. Add a new `canUndo: boolean` state, initialized to `false`,
representing "is the current pending toggle still inside its 3-second undo grace
period" — this is the "still undoable" boolean the task must track separately from
"what optimistic value to display."

`startToggle(nextInStock)`: after the existing `clearTimeout(timerRef.current)` and
`setPending(nextInStock)`, also call `setCanUndo(true)`. Inside the `setTimeout`
callback, keep the existing `onCommitToggle(ingredient.id, nextInStock)` call, but
replace the callback's `setPending(null)` with `setCanUndo(false)` — do not clear
`pending` here. This is the core of the WR-01 fix: once the grace-period timer fires
and the commit is dispatched, `pending` must keep rendering through the mutation's
async round-trip instead of instantly falling back to the stale `ingredient.inStock`
prop.

`undo()`: keep the existing `clearTimeout(timerRef.current)` and `setPending(null)`,
and additionally call `setCanUndo(false)` so an explicitly-undone toggle never leaves
`canUndo` stuck true.

Add a new `useEffect` with dependency array `[canUndo, pending, ingredient.inStock]`
that clears the optimistic override once the server-sourced prop has actually caught
up: when `!canUndo && pending !== null && ingredient.inStock === pending`, call
`setPending(null)`. Gating on `!canUndo` matters — it prevents this effect from firing
during the still-undoable grace window, where `pending` could coincidentally already
equal `ingredient.inStock` (e.g. swiping right on an already-in-stock row). This effect
is what finally releases the optimistic override once `ingredient.inStock` — sourced
from the TanStack Query cache after `useToggleStock`'s `onSettled` invalidation — reflects
the committed value, closing the WR-01 flicker window entirely.

Undo button: change its render guard from `pending !== null` to `canUndo`, so the button
disappears exactly when the grace period elapses (undo is no longer possible), even
though `pending` itself is still set and still driving `displayedInStock` at that point.

WR-02 (unmount flush): the unmount cleanup effect currently only does
`clearTimeout(timerRef.current)`, discarding any commit still inside its grace window
when the row unmounts (e.g. filtered out of view). Because that effect has an empty
dependency array, its closure is frozen at mount and cannot see the latest `pending`,
`canUndo`, `ingredient.id`, or `onCommitToggle` — so add four refs (e.g. `pendingRef`,
`canUndoRef`, `ingredientIdRef`, `onCommitToggleRef`), each initialized via `useRef`
from the corresponding current value, and add one additional `useEffect` with **no**
dependency array (so it runs after every render) whose body reassigns all four refs'
`.current` to the latest `pending`, `canUndo`, `ingredient.id`, and `onCommitToggle`
respectively. Then change the unmount cleanup's returned function to: first
`clearTimeout(timerRef.current)` as before, then — if `canUndoRef.current` is true and
`pendingRef.current !== null` — call
`onCommitToggleRef.current(ingredientIdRef.current, pendingRef.current)` to fire the
commit immediately instead of discarding it. If `canUndoRef.current` is false (the timer
had already fired and the commit already dispatched before unmount), do nothing beyond
the `clearTimeout` — do not double-commit. Calling `onCommitToggle` from this cleanup is
safe: it is owned and closed over by `IngredientList` (via `handleCommitToggle` ->
`toggleStock.mutate`), which persists independently of any single `IngredientRow`
unmounting, so the mutation fires normally even though the row that initiated it is gone.

Update the two comments the review flagged as now-inaccurate: the block comment above
the unmount effect (currently describing "just clear the timer") and the reasoning
inline in `startToggle`'s timeout callback — rewrite both to describe the new
flush-on-unmount and keep-pending-through-commit behavior so the code and its comments
stay in sync (this is a review-driven fix; stale comments would reintroduce the same
kind of confusion that produced WR-01/WR-02).

Do not touch `onCommitToggle`'s prop signature, the `useSwipeable` handlers, the
swipe-direction mapping, the reveal-color/transform rendering, or any other component.
Do not add a test file — component test coverage for this logic is explicitly out of
scope for this task (tracked separately as review finding IN-02).
