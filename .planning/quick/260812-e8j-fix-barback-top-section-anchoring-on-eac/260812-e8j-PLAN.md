# Quick Task 260812-e8j: Fix Barback top-section anchoring on each tab

## Problem

On the Barback app's Ingredients and Recipes tabs, the header block (tab
title + "Add {Item}" button, search bar, quick filter chips) scrolls away
with the list instead of staying pinned at the top of the screen. Confirmed
via screenshots on a real phone: both the title/Add-button row AND the
search bar/filter chips scroll away together when the list is scrolled.

Two compounding bugs cause this:

1. **`App.tsx` has no bounded scroll container.** The outer shell uses
   `min-h-screen` with no `overflow` set, so the actual scrolling happens at
   the document/window level, not inside a CSS scroll container owned by the
   app. `position: sticky` (already used by the search bar wrapper inside
   `IngredientList`/`RecipeList`) only reliably pins relative to a genuine
   scrolling ancestor — against window-level scroll on mobile Safari (with
   toolbar collapse/expand changing the viewport height mid-scroll) it is
   exactly the class of thing that breaks intermittently.

2. **The title+Add-button row was never made sticky at all.** It lives in
   `IngredientsTab.tsx`/`RecipesTab.tsx`, as a separate sibling above
   `IngredientList`/`RecipeList` (which owns the sticky search bar). Only
   the search bar attempted to pin; the title row above it had no
   positioning and always scrolled away.

## Root Cause Fix

1. **`App.tsx`**: give the outer shell a bounded height (`h-dvh`) with
   `overflow-hidden`, and wrap the active tab's content in a
   `flex-1 min-h-0 overflow-y-auto` div — one genuine CSS scroll container
   replacing document/window scrolling. `BottomTabBar` stays exactly as-is
   (already `position: fixed` per quick task 260812-drh, which removes it
   from flex-height accounting entirely — the new wrapper still receives
   the full `h-dvh` height regardless of the tab bar).

2. **`IngredientsTab.tsx` / `RecipesTab.tsx`**: lift the search/filter state
   (`query`, `categoryId` for Ingredients; `query` for Recipes) up from
   `IngredientList`/`RecipeList` into the tab component, and merge the
   title+Add-button row with the search/filter control into ONE
   `position: sticky; top: 0` wrapper — now reliably pinned because it sits
   inside the real scroll container from step 1. This is the smallest-diff
   option of the ones considered: `SearchFilterBar` is already a pure
   controlled component owning no state of its own, so lifting the two
   pieces of state it already expected as props up one level, and rendering
   it from the tab instead of from the list, requires no new components and
   no change to `SearchFilterBar.tsx`'s props or `IngredientList`/
   `RecipeList`'s filtering logic (the `useMemo`, and all four loading/
   error/true-empty/filtered-empty states) — only where that state is
   declared and where the search control renders.

3. **`SettingsTab.tsx`**: no change. It has no search/filter bar and no
   scrolling list — it's a fixed 2-item menu — so there's no header-vs-list
   split to make. It automatically inherits the new bounded scroll
   container from `App.tsx` (harmless no-op today; only matters if the
   settings menu ever grows past one screen).
