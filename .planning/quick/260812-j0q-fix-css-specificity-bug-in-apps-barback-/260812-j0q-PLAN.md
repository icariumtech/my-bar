<objective>
Fix a confirmed CSS cascade-layer bug in the Barback app: `.safe-area-inset-top` in `apps/barback/src/index.css` is a plain, unlayered author rule (`padding-top: env(safe-area-inset-top)`), while Tailwind v4's generated `pt-lg` utility lives inside `@layer utilities`. Per the CSS cascade-layers spec, any unlayered rule always beats any layered rule for the same property, regardless of source order or specificity — so on any device/browser where `env(safe-area-inset-top)` resolves to `0px` (typical Android phone, desktop Chrome — i.e. every non-notched device), `.safe-area-inset-top` silently zeroes out whatever `pt-lg` set, no matter what `pt-*` value is used. This is the real, root-caused reason the prior two "add top padding" quick tasks (260812-fpi's original `pt-md`, then 260812-gcp's bump to `pt-lg`) never produced a visible top gap.

Purpose: Make `.safe-area-inset-top` additive — matching the pattern its sibling `.safe-area-inset-bottom` already correctly uses (`padding-bottom: calc(env(safe-area-inset-bottom) + 16px)`) — so the top padding is baked into the one CSS rule that actually wins the cascade, instead of relying on a second utility class that a cascade-layer boundary silently discards.

Output: `.safe-area-inset-top` produces `--spacing-lg` (24px) of top padding on every device, plus any additional device safe-area inset on notched hardware. The now-redundant `pt-lg` class is removed from both sticky header wrappers. Both tab files' leading comment blocks are corrected to record why the 260812-gcp fix never took visual effect and how this fix resolves it.
</objective>
