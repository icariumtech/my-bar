# Quick Task 260813-ea3: Restyle Patron app to match neon-glow dark-bar-menu reference

## Problem

Phase 3's Patron browse experience (just shipped) is functionally complete but
visually flat: solid `bg-patron-surface` card blocks with pill-chip tags, a
plain icon-only vertical rail with no container, and a flat gradient
placeholder in the detail view. The user wants it re-skinned to match the
neon-glow "backlit bar menu" aesthetic of two reference photos (an existing
commercial iPad bar-menu product, used purely as a visual/mood reference —
`reference/reference-1-menu-list.jpg` and `reference/reference-2-detail-modal.jpg`).

Signature elements to reproduce: a pill-shaped vertical icon rail with a
glowing orange outline around the whole rail AND around each individual icon
button; a soft layered neon box-shadow glow (the recurring visual motif —
implemented once as reusable CSS, not repeated inline); rounded card/detail
containers with glowing orange borders; drink-name-bold + orange-uppercase
middot-separated mood-word typography (replacing pill chips); light
cyan-white ingredient text; a circular glowing close/back control; and a
radial-gradient dark hero placeholder in the detail view.

**Locked and must NOT change:** the makeable-status color mapping (success
green `#10b981` = "Available", destructive red `#ef4444` = "Not Available",
strict two-way collapse per D-42 — no third yellow state), the existing
`--color-patron-*` design tokens in `index.css` (extend, never remove), and
all behavioral/data-fetching logic, component props, routing, and ARIA roles
across the 5 files touched below. Not in scope: the reference's scrolling
ticker bar and "NOW PLAYING" pill (both explicitly out of scope per the
design direction) and any change to `apps/barback` or `apps/server`.

**28 existing Patron tests must keep passing.** Read-first check of every
`*.test.tsx` file found exactly one class-based assertion that a visual
change could break: `TagRail.test.tsx` line 91 —
`expect(typeButton).toHaveClass('opacity-40')` — asserting the muted/
non-interactive state of a rail group with zero active tags (D-36). Every
task below preserves the literal `opacity-40` class on that state. No other
test file asserts a specific class name, only text content, ARIA roles/
names, or `aria-label` values (none of which any task below renames).

## Fix

**New reusable glow utilities** (added once, consumed by every other task —
this is the single source of truth for the neon-glow effect, not repeated
inline per point 3 of the design direction). Added as plain CSS classes in
`apps/patron/src/index.css`, immediately after the existing `@theme` block
(every existing token/rule stays untouched):

- `.glow-orange` — `border: 1px solid rgba(255, 107, 53, 0.7)` plus a
  3-layer box-shadow: `0 0 4px rgba(255, 107, 53, 0.85), 0 0 12px rgba(255, 107, 53, 0.55), 0 0 24px rgba(255, 107, 53, 0.3)`.
  The "selected/strong glow" variant — used on the expanded rail pill
  container, the expanded/selected rail icon, the detail-view content
  card, and the close button.
- `.glow-orange-subtle` — `border: 1px solid rgba(255, 107, 53, 0.45)` plus
  `box-shadow: 0 0 3px rgba(255, 107, 53, 0.5), 0 0 8px rgba(255, 107, 53, 0.3)`.
  The "resting" glow — used on non-selected rail icons and makeable
  RecipeCards.
- `.glow-success` — `box-shadow: 0 0 4px rgba(16, 185, 129, 0.85), 0 0 12px rgba(16, 185, 129, 0.5)`
  (no border — layered on top of the existing `bg-patron-success` fill).
  These rgba values are the literal RGB decomposition of the existing
  `--color-patron-success`/`--color-patron-destructive` hex tokens, so the
  glow always matches its functional color exactly and never redefines it.
- `.glow-destructive` — `box-shadow: 0 0 4px rgba(239, 68, 68, 0.85), 0 0 12px rgba(239, 68, 68, 0.5)`.

Each rule gets a one-line leading comment: reusable neon-glow treatment
added for the 260813-ea3 restyle; `.glow-success`/`.glow-destructive` add a
shadow only and never touch fill color, preserving D-42's locked green/red
semantic mapping.

Three tasks apply this system to the rail, the card grid, and the detail
view, matching the three visual zones called out in the design direction.
