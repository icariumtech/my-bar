# Quick Task 260817-l46: Inline "+ Add new category" in IngredientPicker Summary

**IngredientPicker.tsx now offers a sibling "+ Add new category \"X\"" option beside "+ Add new ingredient \"X\"", letting the owner create a bare category directly from the recipe ingredient-line search without being forced through the specific-ingredient creation sub-flow.**

## Performance

- **Duration:** 12 min
- **Tasks:** 2
- **Files modified:** 2

## Accomplishments
- "Add New" options group now carries both a "+ Add new category" and "+ Add new ingredient" entry, each guarded by its own case-insensitive exact-match suppression (`hasExactCategoryMatch` mirroring the existing `hasExactIngredientMatch`)
- Selecting "+ Add new category" creates the category via `useCreateCategory().mutateAsync({ name: trimmed })` and immediately calls `onChange({ categoryId: created.id, ingredientId: null, requiresSpecific: false })` — the exact same immediate create+select behavior CategoryPicker.tsx's own inline "+ Add" already uses, reused here as a direct path rather than delegating to CategoryPicker as a subcomponent
- A category-creation failure surfaces "Couldn't create category — check the name and try again." via a new top-level `createError` render, without disturbing the existing ingredient-creation error path nested inside the `creating` sub-form
- Full TDD RED -> GREEN cycle: four new tests added and confirmed failing against the unmodified component, then confirmed passing after implementation, with all 79 pre-existing tests in the file remaining green throughout (82/82 passing at completion)

## Decisions Made
- Reused CategoryPicker.tsx's exact create+select pattern (mutateAsync -> onChange -> setSearch, catch -> setCreateError) inline inside IngredientPicker.tsx rather than rendering CategoryPicker as a subcomponent, since IngredientPicker's `onChange` contract is the three-field `IngredientPickerValue`, not CategoryPicker's single `categoryId` — matches the plan's stated rationale exactly.
- Added a new top-level `createError` render (`{!creating && createError && ...}`) as a Rule 1 necessity: the plan called for reusing "the same `createError` pattern already in the file," but that existing `<div>` is nested inside `{creating && (...)}` and would never render for a category-creation failure, since selecting "+ Add new category" never sets `creating`. The `!creating` guard prevents a duplicate error render during the ingredient sub-flow, which keeps using its own existing internal error `<div>` unchanged.
