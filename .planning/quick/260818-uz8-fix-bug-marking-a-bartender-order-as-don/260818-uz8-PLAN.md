<objective>
Fix the bug where marking a Bartender order Done does not clear it from the Orders list, and redesign both the Bartender Orders tab and Recipes tab lists from antd `List`/`List.Item` rows to antd `Card`-based list items matching apps/barback's dark bar-surface row convention, adding ingredient names to every card.

Purpose: The Done-clearing bug is a client-side display defect, not a data or invalidation defect — `PATCH /api/orders/:id/done`, the D-60 5-minute done-order retention window in `GET /api/orders`, `useMarkOrderDone`'s cache invalidation, and the `orders:updated` Socket.IO handler are all already correct and covered by passing tests (verified by reading `apps/server/src/routes/orders.ts`, `apps/server/src/routes/orders.test.ts`, `apps/bartender/src/api/socket.ts`, and `apps/bartender/src/api/socket.test.ts`). The actual defect: `OrdersTab.tsx` renders every batch `useOrders()` returns with zero status filtering — so a just-completed order, which the server correctly keeps returning for up to 5 minutes per D-60, renders as an ordinary, indistinguishable active row. To the bartender this looks exactly like "Done didn't clear it." `App.tsx`'s tab-badge count already excludes `'done'` orders (`openOrderCount` filters to `new`/`in_progress` only) — `OrdersTab`'s own list never applied that same rule to what it renders. Separately, both tabs currently use antd `List`/`List.Item` while `apps/barback`'s `RecipeRow.tsx`/`IngredientRow.tsx` establish this codebase's dark, rounded, `bg-bar-surface` card-style row convention (no app currently imports antd's `Card` component, though antd 6.5.4 is already a dependency and its dark-theme `colorBgContainer` token — `apps/bartender/src/App.tsx`'s `ConfigProvider` — is already `#27272a`, the exact same value as `--color-bar-surface`, so a default-styled `Card` will already match that surface color with no extra token overrides needed).
Output: A fixed `OrdersTab.tsx` whose active list correctly stops showing done orders; both `OrdersTab.tsx` and `RecipesTab.tsx` redesigned onto antd `Card` list items carrying ingredient names, with zero behavioral regression on navigation, batching, badges, or search/filter.
</objective>

  <files>apps/bartender/src/components/OrdersTab.tsx, apps/bartender/src/components/OrdersTab.test.tsx</files>
  <behavior>
    - Given `useOrders()` returns a 'new' order for one recipe and a 'done' order (simulating the server's D-60 retention window still returning it) for a DIFFERENT recipe, `OrdersTab` renders the 'new' recipe's row but the 'done' recipe's name does not appear anywhere in the rendered output.
    - Given `useOrders()` returns ONLY a 'done'-status order (e.g. the instant after a Done tap settles, while still inside the server's 5-minute retention window), `OrdersTab` renders the "No orders yet" / "Queue is empty..." empty state — not a stray row for that done order.
    - Regression guard: a 'new' batch and an 'in_progress' batch for the SAME recipe still render as two separate, non-merged rows exactly as before (the existing `batchOrders` never-merges-across-statuses contract is unrelated to this fix and must not change).
  </behavior>
  <action>
    Root cause (confirmed by reading the server route, its test file, `useMarkOrderDone.ts`, and `socket.ts` — all already correct and already tested): `OrdersTab` derives `batches` from every order `useOrders()` returns and renders ALL of them uniformly, with no status filter. The server's D-60 retention window deliberately keeps a 'done' order in `GET /api/orders`'s response for up to 5 minutes, so a just-completed order keeps rendering as an ordinary, visually-identical active row for that whole window — this is what reads as "Done doesn't clear it." `App.tsx`'s `openOrderCount` badge already filters to `new`/`in_progress` only; `OrdersTab`'s own list never applied that same exclusion to what it displays.

    Fix in `OrdersTab.tsx`: change `const batches = useMemo(() => batchOrders(rawOrders), [rawOrders])` to compute a `visibleBatches` value that additionally filters out any batch whose `status === 'done'` — e.g. `useMemo(() => batchOrders(rawOrders).filter((batch) => batch.status !== 'done'), [rawOrders])`. Do NOT change the exported `batchOrders` function itself — its pure grouping/sorting contract (and its own `describe('batchOrders', ...)` test block) is unrelated to which statuses get displayed and must keep passing unmodified. Replace every remaining reference to the old `batches` variable (the `batches.length === 0` empty-state check and the list's `dataSource`) with `visibleBatches`. Add a short code comment at the filter site explaining WHY: the server's D-60 retention window intentionally keeps a 'done' order queryable for 5 minutes, but the Orders tab's active queue must only ever show open work — mirrors the same `new`/`in_progress`-only rule `App.tsx`'s `openOrderCount` badge already applies, now applied consistently to the list itself.

    In `OrdersTab.test.tsx`: add `status: 'done'` order fixtures as needed (via the existing `makeOrder` helper) to prove the three behaviors above. Keep all pre-existing tests passing unmodified.
